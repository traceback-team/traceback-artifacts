TRACEBACK은 이 일반 경로에 무엇을 사용하나요?

고객 요청은 Vercel 프런트 → Route 53 A 레코드·EIP → EC2의 Nginx·Django → private RDS로 구성합니다. 배포는 GitHub Actions → AWS OIDC 권한 → ECR 이미지 → SSM 명령 → EC2 Docker로 구성합니다. DNS/EIP·EC2 도구·ECR pull 권한·Vercel rewrite는 준비됐습니다. TLS 인증서·443 프록시·서버 환경 파일·앱 배포는 아래 상태 흐름에서 미완료로 표시합니다.

CI가 통과했는데도 브라우저에서 API가 실패할 수 있나요?

그렇습니다. CI는 코드·이미지·임시 테스트 환경을 검사합니다. DNS 이름이 실제 서버 IP를 알려줘도, 서버의 443 수신 프로그램과 TLS 인증서, reverse proxy, 앱, DB 연결이 없으면 브라우저 요청은 끝까지 통과하지 못합니다. 그래서 아래 설정 순서에서 각 경계를 따로 확인합니다.

GitHub Actions는 어떤 값으로 AWS에 접근하나요?

결론부터 보면 AWS_DEPLOY_ROLE_ARN은 AWS에서 맡을 IAM 역할을 지정하고, DEVELOPMENT_INSTANCE_ID는 배포할 EC2를 지정합니다. 두 값은 같은 목적이 아니며, 둘 다 비밀번호나 Access Key가 아닙니다.

GitHub가 AWS 비밀번호 없이 어떻게 배포할 수 있나요?

GitHub Actions 실행은 OIDC 토큰으로 자신의 저장소·브랜치 또는 Environment 정보를 증명합니다. AWS의 역할 신뢰 정책이 이를 확인하면 STS가 잠시 쓸 자격 증명을 발급합니다. 그 역할의 정책이 ECR push와 SSM 명령 범위를 결정합니다. AWS_DEPLOY_ROLE_ARN은 이 역할의 주소이며, 비밀 자격 증명 자체가 아닙니다. AWS: OIDC 역할 신뢰

왜 GitHub 역할과 EC2 역할을 따로 두나요?

GitHub runner는 이미지를 게시하고 대상 인스턴스에 배포 명령을 보냅니다. EC2는 자신에게 붙은 역할로 이미지를 내려받아 실행합니다. 두 작업의 주체와 필요한 API 권한이 다릅니다. 사람의 로컬 SSM 세션 시작 권한도 이 둘과 별도로 관리합니다. SSM의 신원 구분 보기

DEVELOPMENT_INSTANCE_ID“SSM 명령을 어느 EC2로 보낼까?”에 답합니다. 현재 대상은 i-051f85a1ac4e64a2c. 개발 전용 스크립트가 이 값을 공통 배포 실행기에 넘깁니다. AWS에 인증하거나 권한을 부여하는 값이 아닙니다.
AWS_REGION리소스가 있는 AWS 리전. 현재 ap-northeast-2 (서울)입니다. STS 자격 증명을 받는 호출과 ECR/SSM 요청에 함께 쓰입니다.
ECR_REPOSITORY이미지 저장소 이름 traceback. 계정 ID와 리전이 포함된 전체 주소는 ECR login/build action이 구성합니다.
IAM에서 구분할 두 질문: Trust relationship은 “누가 이 역할을 맡을 수 있나?”를 정합니다. Permission policy는 “맡은 뒤 무엇을 할 수 있나?”를 정합니다. GitHub OIDC provider와 trust policy가 전자, ECR/SSM 정책이 후자입니다. EC2 instance role은 별도의 주체와 별도 권한입니다. 실제 정책 문서는 docs/deployment.md의 OIDC·정책 절에 있습니다.
AWS 계정의 GitHub 배포 역할

traceback-development-deploy

GitHub Actions 실행이 OIDC로 임시 사용합니다. 역할의 Trust relationship은 지정된 GitHub OIDC provider를 신뢰하고, sub를 repo:traceback-team/traceback:environment:development로 제한합니다. 따라서 다른 저장소나 Environment는 이 역할을 맡지 못합니다.

  • 허용: ECR traceback에 이미지 push 및 이미지 조회
  • 허용: 지정된 EC2에 SSM Run Command 전송·결과 조회
  • 불허: IAM 역할 생성/수정, 계정 관리자 권한, 임의 EC2 조작

GitHub workflow는 permissions: id-token: write를 선언하고 aws-actions/configure-aws-credentials에서 이 역할 ARN을 가리킵니다. AWS access key secret은 없습니다.

EC2 인스턴스에 붙는 실행 역할

traceback-development-ec2

인스턴스 프로파일을 통해 EC2 안의 AWS CLI/Docker가 사용합니다. 배포 명령 중 EC2가 ECR에서 이미지를 가져오려면 pull 권한이 필요합니다.

  • 현재 연결됨: AmazonSSMManagedInstanceCore (SSM Agent 관리 통신)
  • 현재 연결됨: 저장소 traceback의 ECR pull 전용 정책. EC2의 ECR 인증도 확인
  • 지금은 부여하지 않음: S3 쓰기 권한. 업로드 코드/경로가 생길 때 필요한 bucket prefix만 허용

아직 배포되지 않은 이유: PR에서 Quality/Test는 통과했지만 development push가 없어 이미지 빌드·ECR push·EC2 배포 job이 실행되지 않았습니다. 서버 런타임 .env와 TLS 설정도 남았습니다.

GitHub deploy role에 붙인 Permissions policy

정책은 작업에 필요한 서비스 API와 대상 자원을 묶습니다

ECR 인증ecr:GetAuthorizationToken — Docker가 ECR 로그인 token을 받습니다. 이 API는 repository ARN 하나로 제한할 수 없어 Resource *가 필요합니다.
ECR 이미지 동작저장소 traceback ARN에만 DescribeRepositories, DescribeImages, push에 필요한 layer upload·PutImage 권한을 허용합니다.
SSM 배포 요청ssm:SendCommand를 AWS 관리 문서 AWS-RunShellScript와 개발 EC2 i-051f85a1ac4e64a2c에 함께 범위 지정합니다. SSM을 통해서만 서버 명령이 들어가고 SSH 22는 열지 않습니다.
SSM 결과 확인ssm:GetCommandInvocation은 배포 성공 여부와 출력을 가져옵니다. 현재 이 API 권한은 AWS가 지원하는 리소스 ARN 범위 제한이 어려워 Resource *를 사용합니다.

최종 JSON과 리전/계정/저장소/인스턴스 ARN을 대입하는 예시는 docs/deployment.md에 있습니다. AWS IAM 화면에서 inline policy 이름 traceback-development-deploy-policy를 확인했습니다.

AWS Seoul → ECR → Private repositories에서 traceback 생성. 태그 변경 불가(immutable), 기본 AES-256 암호화. 현재 repository는 비어 있어 첫 성공 배포 전까지 이미지가 없습니다.

AWS IAM → Identity providers에 provider URL https://token.actions.githubusercontent.com, audience sts.amazonaws.com 등록. GitHub 실행이 서명한 ID token을 AWS가 검증할 수 있게 연결합니다.

전용 deploy role과 Trust relationship 생성

IAM role traceback-development-deploy의 신뢰 대상은 위 OIDC provider 하나로 둡니다. aud=sts.amazonaws.com와 sub=repo:traceback-team/traceback:environment:development 조건으로 scope를 제한했습니다.

최소 권한 policy 연결

역할에 ECR push/조회와 SSM 명령 권한만 넣었습니다. ECR 동작은 저장소 traceback에 범위 지정, SSM 전송 대상은 development EC2로 제한합니다. Access Key를 만드는 절차는 없습니다.

GitHub Environment 변수 등록

AWS_DEPLOY_ROLE_ARN, AWS_REGION, ECR_REPOSITORY, DEVELOPMENT_INSTANCE_ID를 Environment Variables에 저장했습니다. 전부 배포 위치/자원 식별 값이라 secrets가 아니며 `.env.dev.git`은 기록용 목록입니다.

development branch protection 설정

PR 병합과 Quality, Test 통과를 요구합니다. 승인 review는 0명, force push와 branch deletion은 차단. 현재 “Do not allow bypassing”는 켜지지 않아 repository 관리자에게 우회 권한이 남아 있습니다.

남은 EC2 준비를 끝내고 첫 push 검증

ECR pull 권한과 Docker/Compose/AWS CLI, Nginx HTTP는 준비했습니다. 남은 것은 런타임 /opt/traceback/.env, RDS 앱 계정, 인증서와 Nginx 443 프록시입니다. 이 선행 작업 뒤 development push에서 OIDC→ECR→SSM 전체 흐름을 확인합니다.

휴대폰에서도 읽기 쉬운지 확인

ECR을 쓰면 추가 요금이 드나요?

저장소 자체는 월정액이 아닙니다

ECR은 이미지가 저장된 용량과 인터넷 방향 전송량을 기준으로 과금합니다. 저장 이미지가 아직 없는 현재는 ECR repository 이름만 만들어 둔 데서 이미지 저장 비용이 생기지 않습니다. AWS 가격 페이지 예시는 private image storage USD 0.10/GB-month이며, 새 ECR 고객은 첫 1년 동안 private storage 500 MB/month 무료 혜택이 표시됩니다. 계정별 Free Tier 대상 여부를 Billing에서 확인해야 합니다.

현재 흐름의 큰 비용 요인은 이미지 보관량

같은 서울 리전의 ECR↔EC2 데이터 전송은 AWS 가격표상 무료입니다. GitHub-hosted runner에서 ECR로 push하는 전송도 ECR inbound 과금 대상이 아닙니다. 배포 때마다 SHA tag 이미지가 쌓이므로, 오래된 이미지 보관 정책이 없으면 저장 용량이 누적됩니다. 첫 배포 전 수명주기 정책을 정하되, production 승격·rollback에 필요한 digest를 삭제하지 않도록 해야 합니다.

비용 체크: 지금 만든 ECR은 비어 있고 repository 생성 자체에는 월 정액이 없습니다. 첫 image push부터 저장 용량이 계산됩니다. AWS 크레딧은 청구 상한이 아니므로 Amazon ECR 공식 가격표와 Billing을 확인하세요. 화면에 캡처된 immutable tag 설정은 같은 SHA 이름의 이미지를 덮어쓰지 못하게 해 배포 재현성을 높이지만, 이미지를 자동 삭제하지는 않습니다.

더 깊은 접속 인증/SSM 구조는 SSH와 SSM 학습 가이드, 도메인과 DNS는 DNS 가이드, IP 선택은 개발 IP·도메인 가이드에서 공부합니다. 이 문서는 그 자원들을 CI/CD에 연결하는 전체 흐름을 다룹니다.

AWS에 들어갈 권한을 확인했으니, 이제 그 권한으로 어떤 이미지와 명령을 서버에 보내는지 실제 코드로 따라갑니다.

배포 코드는 어떤 순서로 읽으면 될까요?

파일 하나가 모든 일을 하는 구조가 아닙니다. Dockerfile이 실행 이미지를 만들고, CI가 검증하며, 환경별 workflow가 이미지 저장과 서버 배포를 고르고, 공통 스크립트가 SSM으로 EC2에 명령을 보냅니다.

1 · Dockerfile로컬 개발용과 운영용 이미지 만드는 법
2 · Compose 파일 2개공통 설정 + 운영 환경 덮어쓰기
3 · ci.ymlPR/push 검사와 CD 호출 조건
4 · deploy-development.ymldevelopment 이미지 build/push 후 EC2 배포
5 · deploy-production.ymldevelopment에서 검증된 동일 이미지 digest 승격
6 · 환경별 배포 스크립트dev/prod 진입점과 공통 SSM 배포 로직
환경별 스크립트가 있는데 공통 실행기도 쓰는 이유는? deploy-development.sh와 deploy-prod.sh는 서로 다른 EC2 ID를 공통 입력으로 바꾸는 짧은 진입점입니다. 환경별 workflow가 GitHub Environment, IAM 역할과 이미지 선택 규칙을 고릅니다. 실제 ECR pull·migrate·Compose 실행은 deploy-common.sh가 함께 담당하므로 동일한 보안 수정이 dev와 prod에 적용됩니다. 배포 단계가 실제로 달라질 때만 환경별 동작을 분리합니다.

GitHub Actions가 자동으로 ECR에 올리는 지점

development push에서 ci.yml의 Quality와 Test가 먼저 성공해야 deploy-development.yml이 호출됩니다. 그 안의 docker/build-push-action이 Dockerfile의 production target을 빌드하고 push: true로 ECR에 업로드합니다. 이미지 tag는 커밋 SHA이며, 다음 단계는 tag가 아니라 ECR이 부여한 digest를 EC2에 전달합니다. EC2는 직접 Git pull이나 Docker build를 하지 않습니다.

수동으로 ECR에 push하려면

수동 배포는 로컬 컴퓨터에서 Docker build → ECR push → digest 확인 → SSM 배포 순서입니다. Docker Hub는 이 흐름에 필요 없습니다. 아래 예시는 현재 개발 리전/저장소를 사용합니다. 로컬 AWS Identity Center 프로필이 ECR push 권한을 가져야 합니다. GitHub OIDC용 deploy role은 GitHub token만 신뢰하므로, 로컬 프로필이 그 role을 자동으로 대신 쓰지는 않습니다.

명령을 읽는 순서1–3행에서 배포할 커밋을 확인하고, 5–13행에서 로컬 AWS 신원과 ECR 주소를 정합니다. 15–19행은 이미지 빌드·push, 21–26행은 digest 확인, 28–30행은 SSM 배포 호출입니다. 이 코드는 사람이 실행하는 예시이며 저장소 스크립트의 원본 행 번호가 아닙니다.
실행 예시 · 로컬에서 ECR에 수동 배포예시 행 번호 · 저장소 원본 행과 다름
# 반드시 빌드할 커밋의 저장소 상태가 깨끗한지 확인git status --shorttest -z "$(git status --porcelain)" || { echo "Commit or discard local changes before publishing" >&2; exit 1; }# 로컬 AWS SSO 프로필로 로그인한 다음 ECR 대상을 정함export AWS_PROFILE=traceback-devexport AWS_REGION=ap-northeast-2aws sso login --profile "$AWS_PROFILE"export AWS_ACCOUNT_ID="$(aws sts get-caller-identity --query Account --output text)"export ECR_REPOSITORY=tracebackexport IMAGE_TAG="$(git rev-parse HEAD)"export ECR_REGISTRY="${AWS_ACCOUNT_ID}.dkr.ecr.${AWS_REGION}.amazonaws.com"export IMAGE_URI="${ECR_REGISTRY}/${ECR_REPOSITORY}:${IMAGE_TAG}"# ECR 로그인, 운영 이미지 빌드, 업로드aws ecr get-login-password --region "$AWS_REGION" \  | docker login --username AWS --password-stdin "$ECR_REGISTRY"docker build --platform linux/amd64 --target production --tag "$IMAGE_URI" .docker push "$IMAGE_URI"# 배포에 쓸 불변 digest 조회export IMAGE_DIGEST="$(aws ecr describe-images \  --repository-name "$ECR_REPOSITORY" \  --image-ids "imageTag=$IMAGE_TAG" \  --query 'imageDetails[0].imageDigest' --output text)"export APP_IMAGE="${ECR_REGISTRY}/${ECR_REPOSITORY}@${IMAGE_DIGEST}"# 준비가 끝난 development EC2에 SSM으로 배포export DEVELOPMENT_INSTANCE_ID=i-051f85a1ac4e64a2cbash .github/scripts/deploy-development.sh
수동 실행 전 조건: Docker 플랫폼이 EC2 CPU와 맞아야 해서 현재 t3 계열용으로 linux/amd64를 명시합니다. ECR tag는 immutable이므로 같은 SHA tag를 다시 덮어쓸 수 없습니다. 로컬 IAM 자격에는 ECR push와 SSM 대상/명령 조회 권한이 필요하고, EC2 instance role에는 ECR pull 권한이 필요합니다. EC2의 pull 권한은 준비됐지만 서버 .env·RDS 앱 계정·TLS가 없어 지금 실행해도 실사용 배포가 완료되지는 않습니다.

파일별 맡은 일

Dockerfile · 실행 이미지

base에 Python과 고정 버전의 uv를 준비하고, 개발/운영 의존성을 다른 build stage에서 설치합니다. 운영 stage는 개발 도구를 빼고 앱 코드를 복사한 뒤 권한이 제한된 app 사용자로 Gunicorn/ASGI를 실행합니다.

docker-compose.yml · 로컬 개발 기본값

Django 개발 서버와 PostgreSQL을 정의합니다. .:/app은 코드 변경을 컨테이너에서 바로 보는 bind mount입니다. postgres_data는 로컬 DB 데이터가 담기는 이름 있는 Docker volume입니다.

docker-compose_prod.yml · 운영 overlay

기본 Compose 설정에 운영 이미지를 지정하고 개발 서버 명령·DB 의존성을 제거합니다. db: !reset null로 Postgres 컨테이너를 빼고, volumes: !reset []로 소스 bind mount를 제거합니다. 운영 DB는 RDS, 업로드 파일은 S3에 두므로 EC2의 Compose volume에 영구 업무 데이터를 보관하지 않습니다.

.github/workflows/ci.yml · 검사와 갈림길

PR에서는 Quality/Test를 실행하고, main PR에서는 운영 이미지의 컨테이너 smoke test도 실행합니다. development push에서 검사 둘이 성공하면 development workflow를 호출하고, main push에서만 production workflow를 호출합니다.

deploy-development.yml · build/push/development 배포

GitHub OIDC로 개발 deploy role을 맡습니다. ECR tag 규칙을 확인하고, 같은 SHA 이미지가 이미 있으면 재사용합니다. 없으면 운영 target 이미지를 build/push합니다. 이후 deploy-development.sh에 이미지와 개발 EC2 ID를 넘깁니다.

볼륨은 환경마다 다르게 다룹니다

로컬에서 docker compose down을 하면 컨테이너는 내려가지만 postgres_data는 남아 다음 실행에도 DB 데이터가 유지됩니다. docker compose down -v는 이 로컬 DB 볼륨까지 삭제하므로 초기화할 때만 사용합니다. 운영 overlay는 소스 bind mount와 Postgres 서비스를 제거하고 명시적 Docker volume도 비웁니다. 운영 데이터는 RDS/S3에 남고 EC2에는 실행 중인 컨테이너와 내려받은 이미지 layer가 저장됩니다. EC2 디스크 정리는 DB 볼륨 삭제와 별개이며, 과거 이미지가 rollback에 필요한지 확인한 뒤 보관/정리 정책을 둡니다. docker system prune --volumes처럼 volume까지 한꺼번에 지우는 명령은 운영 서버에서 피합니다.

인바운드 · 외부에서 EC2로 들어오는 연결

80/443 공개, SSH는 닫힘

  • TCP 443 HTTPS → 0.0.0.0/0: 인터넷 전체에서 HTTPS 접근 허용. 공개 웹 API를 제공할 때 일반적인 규칙입니다.
  • TCP 80 HTTP → 0.0.0.0/0: HTTP→HTTPS 이동 또는 HTTP-01 인증서 발급에 사용합니다. DNS-01 인증만 쓴다면 열지 않아도 됩니다.
  • TCP 22 SSH 규칙 없음: 관리 접속은 SSM 경로를 사용합니다. SSH 접속을 위해 22번을 열 필요가 없습니다.
  • 주의: 보안 그룹이 443을 허용해도 인증서와 수신 설정이 없으면 HTTPS는 열리지 않습니다. Nginx HTTP 80은 이미 외부에서 응답하며, 앱 배포 뒤 OS 방화벽과 Nginx 응답을 다시 확인합니다.
아웃바운드 · EC2에서 밖으로 나가는 연결

전체 IPv4 트래픽 허용

현재 EC2 보안 그룹에는 모든 프로토콜·포트에서 0.0.0.0/0으로 나가는 규칙 한 개가 있습니다. ECR 이미지 다운로드, SSM, 패키지 업데이트, HTTPS 외부 호출 등은 가능하지만 목적지와 포트를 제한하지 않은 넓은 규칙입니다. 보안 그룹은 상태 저장 방식이라 허용된 요청에 대한 응답 트래픽은 별도 인바운드 규칙이 필요하지 않습니다.

첫 개발 배포: 이 설정은 AWS 생성 시 자주 보이는 기본 outbound 정책입니다. 기능상 바로 막히는 항목은 아니지만 최소 권한 정책은 아닙니다. egress를 제한하려면 SSM, ECR API/registry, ECR layer용 S3, 운영체제 업데이트, SES SMTP(사용 시) 목적지를 고려해 테스트하며 좁혀야 합니다. 아직 VPC endpoint/NAT 구성을 추가할 필요는 확인되지 않았습니다.

RDS 보안 그룹

5432는 개발 EC2 보안 그룹만 허용

RDS의 rds-ec2-1 인바운드 규칙은 PostgreSQL TCP 5432이고, source는 CIDR 전체가 아니라 EC2용 ec2-rds-1 보안 그룹 ID입니다. RDS 콘솔에서 인터넷 액세스 게이트웨이가 비활성이라고 확인했습니다. RDS 자체 아웃바운드 규칙은 없습니다. 이 구조는 개발 DB에 인터넷에서 직접 연결하지 않도록 하는 좋은 경계입니다.

EC2→RDS 연결을 실제 확인하려면 Compose `.env`에 RDS endpoint와 앱 전용 DB 계정을 지정한 뒤 Django migration/health check까지 통과해야 합니다. 현재 앱 DB 계정과 EC2 `.env`는 아직 미설정입니다.

배포 전에 확인할 네트워크 항목

  • 라우트 테이블: EC2가 쓰는 main 테이블의 0.0.0.0/0 → Internet Gateway 경로와 상태를 확인 — 2026-10-03 콘솔에서 활성 확인.
  • 서브넷 연결: EC2 서브넷은 명시적 연결이 없고 main 테이블을 사용 — 콘솔에서 확인.
  • 서브넷 연결 네트워크 ACL의 인바운드·아웃바운드 규칙과 응답용 임시 포트는 아직 별도 확인 필요.
  • RDS의 Publicly accessible이 꺼져 있고, DB subnet group의 서브넷이 모두 같은 VPC인지 확인.
  • RDS inbound 5432가 EC2 전용 SG만 source로 쓰는지 유지. 현재 콘솔에서 확인됨.
  • 첫 배포 후 외부에서 80/443만 접근되고 앱 8000은 공개되지 않는지 확인. SSH 22는 열지 않음.

  • 단순하고 저렴한 시작: 공개 서브넷에 EC2+Nginx, 보안 그룹 80/443, SSM 관리, 같은 VPC의 private RDS. 현재 TRACEBACK의 의도입니다.
  • 현재 콘솔: 기본 VPC·기본 public subnet을 사용하고, DB는 인터넷 경로를 비활성화했으며 EC2 SG source만 허용합니다.
  • 추가로 필요한 앱 구성: Nginx HTTP·Docker/Compose/AWS CLI·EC2 ECR pull IAM은 준비됐습니다. TLS 인증서·Nginx 443 프록시, /opt/traceback/.env, Django 앱 DB 계정과 이미지 배포가 남았습니다.
  • 향후 강화: dedicated VPC에서 public proxy/app과 private DB subnet 분리, 목적지별 egress, VPC flow logs/CloudTrail 비용 검토. 초기 실사용 검증에 필수인 별도 VPC endpoint/ALB는 아닙니다.
처음 만드는 사람용: 라우팅 테이블·보안 그룹 설정 순서

라우팅 테이블은 서브넷 단위 경로표이고, 보안 그룹은 인스턴스/네트워크 인터페이스의 상태 저장 방화벽입니다. 둘은 서로 대체하지 않습니다.

  1. EC2 서브넷의 route table 찾기: VPC Console → Subnets → EC2 서브넷 → Route table 탭에서 연결된 테이블을 엽니다. 명시적 연결이 없다면 VPC의 main route table을 씁니다. 현재 TRACEBACK은 rtb-04258608476a79e32입니다.
  2. 공개 서브넷 경로 확인: Routes에 VPC CIDR의 local 경로와 0.0.0.0/0 → igw-… 경로가 있고 상태가 active인지 확인합니다. 경로만 있어도 EC2에 public IPv4/EIP가 없으면 일반 인터넷 응답이 되지 않습니다. 현재 기본 경로는 인터넷 게이트웨이로 활성 상태입니다.
  3. EC2 보안 그룹 inbound: EC2 → Security Groups → Inbound rules. 공개 HTTPS 서비스면 TCP 443, source 0.0.0.0/0; HTTP→HTTPS redirect/HTTP-01 인증서 발급이 필요하면 TCP 80도 같은 source로 추가합니다. SSM을 쓸 때 SSH TCP 22는 열지 않습니다. 앱 포트 8000은 공개하지 않습니다.
  4. EC2 보안 그룹 outbound: 현재는 모든 프로토콜·포트, destination 0.0.0.0/0 한 규칙입니다. 첫 개발 배포에는 이 기본값으로 동작 여부를 확인하되, 제한할 때는 SSM HTTPS, ECR API/registry HTTPS, ECR layer용 S3, OS 패키지 저장소, 필요한 외부 API/SMTP를 목록화하고 시험합니다. 공용 패키지 저장소는 목적지 주소가 바뀔 수 있어 CIDR만으로 좁히기 어려울 수 있습니다.
  5. RDS 보안 그룹: inbound PostgreSQL TCP 5432의 source에 CIDR이나 EC2 public IP 대신 EC2 보안 그룹을 지정합니다. RDS public accessibility는 끄고 앱 전용 DB 계정을 씁니다. 현재 source 그룹 방식은 설정됨. 실제 연결은 앱 환경변수 설정 후 검증해야 합니다.
  6. Network ACL 확인: VPC → Network ACLs에서 해당 서브넷의 inbound/outbound rule, 포트, ephemeral response ports를 확인합니다. NACL은 stateless이므로 양방향 규칙이 필요합니다. TRACEBACK의 현재 NACL 세부 규칙은 아직 확인하지 않았습니다.
현재 상태 요약: route table의 IGW 기본 경로와 main 연결, EC2 inbound 80/443 및 outbound 전체 허용, RDS inbound 5432의 EC2 SG source는 콘솔에서 확인했습니다. NACL 세부 규칙과 좁힌 egress는 미완료 확인 항목입니다. 실제 첫 외부 HTTPS 요청과 EC2→RDS 연결은 배포 후 시험해야 합니다.

네트워크가 EC2까지 도착한 다음에는 누가 HTTPS를 받아 Django에 넘기는지 결정해야 합니다. 여기서 Nginx와 로드 밸런서의 위치를 비교합니다.

Nginx는 어디에 두는 게 일반적인가요?

Nginx는 HTTP 요청을 받아 다른 서버나 프로세스로 전달하는 웹 서버·reverse proxy입니다. “EC2 안”은 EC2 호스트에서 실행한다는 뜻이고, “앞단 별도”는 Nginx 전용 머신이나 AWS 관리형 Load Balancer가 앱 인스턴스보다 먼저 요청을 받는 구조입니다. 규모와 가용성 요구에 따라 선택합니다.

왜 Django 컨테이너를 443에 바로 노출하지 않고 앞단을 두나요?

앞단은 브라우저의 HTTPS 연결을 받고 인증서를 제시한 다음 내부 앱으로 요청을 전달합니다. 이 지점에서 TLS 갱신, HTTP→HTTPS 이동, 요청 로그와 제한을 관리할 수 있습니다. 단일 EC2에서는 Nginx를 호스트나 컨테이너로 둘 수 있고, 규모가 커지면 관리형 Load Balancer를 앞단에 둘 수도 있습니다. TRACEBACK은 초기 비용과 운영 범위를 고려해 같은 EC2의 호스트 Nginx를 선택했습니다. Nginx HTTP는 설치·확인했고 TLS·443 프록시 연결은 남아 있습니다.

일반 패턴 비교현재 TRACEBACK 선택: 같은 EC2의 호스트 Nginx
소규모 · 단일 서버

Nginx를 앱 EC2 호스트에 설치

인터넷→EC2 보안 그룹 80/443→Nginx (EC2 host)→127.0.0.1:8000 Docker 앱

요청이 어떻게 흐르나: Vercel이 https://api.dev-traceback.com에 요청합니다. Route 53이 EIP를 알려주고, EC2의 443에서 Nginx가 TLS를 끝낸 뒤 Docker 안의 Django로 전달합니다. Django는 private 경로로 RDS에 연결합니다.

  • 좋은 점: 별도 LB나 Nginx 서버 비용이 없고 구조가 작아 배우기 쉽습니다.
  • 감수할 점: 한 EC2가 장애 나면 Nginx와 앱이 함께 중단됩니다. OS 보안 업데이트, Nginx 설정, 인증서 갱신을 직접 관리합니다.
  • 보안 경계: 외부에는 80/443만 열고 앱 8000은 localhost에만 bind합니다. RDS 5432는 EC2 보안 그룹에서만 허용합니다.

우리 선택: 지금 dev는 이 방식입니다. 배포 스크립트는 docker-compose.yml과 docker-compose_prod.yml을 함께 읽습니다. 기본 파일의 127.0.0.1:8000:8000 게시 설정은 운영 오버레이와 합쳐진 결과에도 남아 있으므로, 호스트 Nginx가 EC2 내부에서 앱에 연결할 통로는 준비되어 있습니다. 이 포트는 loopback에만 묶여 외부 인터넷에 직접 공개되지 않습니다.

같은 EC2 · Nginx도 컨테이너

Nginx를 Docker Compose 서비스로 실행

인터넷→EC2 80/443→Nginx 컨테이너→Docker 내부망의 Django

별도 서버를 만드는 방식은 아닙니다. 호스트 Nginx처럼 EC2 한 대에서 동작하지만, Nginx 프로세스도 컨테이너로 포장해 Compose가 앱과 함께 관리합니다.

  • 좋은 점: Nginx 버전과 설정을 이미지/코드로 관리하고 호스트 패키지 설치를 줄일 수 있습니다.
  • 감수할 점: Compose 네트워크와 인증서 파일·갱신, Nginx 컨테이너 재시작 의존성까지 직접 설계해야 합니다.
  • 중요: 컨테이너로 옮겨도 장애 경계와 서버 비용은 여전히 EC2 한 대 기준입니다.

현재 선택은 아님: 이 프로젝트의 Nginx 예시는 호스트에 설치하는 구성을 전제로 합니다. 컨테이너 방식으로 바꾸려면 Compose 네트워크와 TLS 보관·갱신을 함께 바꿔야 합니다.

여러 앱 서버 · 확장/가용성

관리형 ALB를 앱 EC2 앞에 둠

인터넷→ALB 443 + 인증서→target group / health check→EC2 앱들

요청이 어떻게 흐르나: AWS Application Load Balancer가 외부 HTTPS 연결을 받고 인증서를 사용해 TLS를 끝낼 수 있습니다. Listener 규칙이 건강한 target에 요청을 전달하고, 여러 EC2·가용 영역으로 분산할 수 있습니다.

  • 좋은 점: 인스턴스 여러 대로 요청 분산, health check, host/path routing, 인증서 관리를 AWS에서 제공받습니다.
  • 감수할 점: ALB 시간·처리량 요금과 대상 보안 그룹, target group, listener 등 설정이 추가됩니다. 앱 인스턴스 한 대만 두면 그 인스턴스 장애를 해결하지 못해 고가용성이 완성되지는 않습니다.
  • Nginx는 필수 아님: 앱 앞의 라우팅과 TLS를 ALB가 담당하면 Django/Gunicorn으로 직접 전달할 수 있습니다. 앱별 특별한 proxy 설정이 필요하면 ALB 뒤에 Nginx를 둘 수 있지만, 두 겹으로 둘 이유가 있는지 확인합니다.

일반적인 사용 시점: 여러 EC2로 수평 확장하거나 가용 영역 간 장애 대응이 필요할 때 선택합니다. AWS는 ALB를 대상 그룹과 health check를 사용해 여러 target으로 HTTP/HTTPS를 라우팅하는 관리형 서비스로 설명합니다.

특별한 네트워크 요구

Nginx 전용 EC2를 따로 운영

인터넷→Nginx 전용 EC2→private 앱 EC2→RDS

요청이 어떻게 흐르나: 공개 프록시 서버가 TLS와 reverse proxy를 담당하고 앱 서버는 private subnet에 둘 수 있습니다. 이때 프록시 서버와 앱 서버 사이의 보안 그룹 규칙·장애 대응도 직접 설계해야 합니다.

  • 가능한 이유: 프록시 계층을 앱 호스트와 분리하거나 여러 내부 서비스에 공통으로 붙이는 특수한 요구가 있을 수 있습니다.
  • 감수할 점: EC2 한 대와 운영 대상이 추가되고, 그 Nginx가 단일 장애 지점이 될 수 있습니다. 고가용성을 얻으려면 프록시도 여러 대와 앞단 분산이 필요합니다.
  • 실무 판단: AWS에서 단순히 “서버를 나누고 싶다”는 이유라면 전용 Nginx EC2부터 늘리기보다 ALB 같은 관리형 진입점이 요구에 맞는지 비교합니다.

우리 현재 선택은 아님: dev는 EC2 한 대이고 앞단 전용 인스턴스를 따로 두지 않습니다.

TLS 종료란? 브라우저/Vercel과 HTTPS로 암호화된 연결을 Nginx나 ALB가 받아 인증서를 제시하고 복호화하는 위치를 말합니다. 현재 계획에서는 EC2 호스트 Nginx가 인증서를 사용합니다. ALB 패턴에서는 보통 HTTPS listener에 인증서를 연결합니다. 한 연결의 어느 지점에서 TLS가 끝나는지 알아야 Django에 올바른 scheme/host 정보를 전달하고 secure cookie·CSRF를 검증할 수 있습니다.

도메인이 생긴 다음 HTTPS를 여는 순서

HTTPS는 도메인 이름 + 그 이름의 소유를 확인해 발급받은 TLS 인증서 + 인증서를 제시할 웹 서버가 함께 있어야 합니다. 이 프로젝트의 Nginx 설정 예시는 인증서 파일이 이미 있다고 가정하므로, 파일을 바로 활성화하면 인증서 경로가 없어 Nginx 시작에 실패할 수 있습니다.

① DNS·포트 80 확인A 레코드가 EC2 EIP를 가리키고 보안 그룹이 80을 받는지 확인합니다. TRACEBACK은 두 설정을 확인했습니다.
② HTTP 검증 경로 열기Nginx를 설치하고 인증서가 없어도 시작 가능한 임시 HTTP 설정에서 /.well-known/acme-challenge/를 제공합니다. TRACEBACK은 외부에서 응답을 확인했습니다.
③ ACME 인증서 발급예: Let's Encrypt의 ACME client가 위 경로로 도메인 소유를 검증한 뒤 인증서·개인 키를 저장합니다. 발급과 갱신은 아직 미설정입니다.
④ 443 프록시와 외부 검사인증서 경로를 확인한 뒤 Nginx 설정을 활성화하고 설정 검사·재시작을 합니다. HTTPS 응답, 갱신 시험, Django proxy header를 확인합니다. 아직 미검증입니다.

server {    listen 80;    server_name api.dev-traceback.com;    location /.well-known/acme-challenge/ {        root /var/www/certbot;    }}

HTTP-01은 80 포트로 파일을 확인합니다. DNS-01은 DNS 레코드로 확인하는 대안입니다. 인증서 자동 갱신 timer와 갱신 뒤 Nginx reload hook까지 확인해야 운영이 끝납니다. Amazon Linux 2023 TLS 안내 · Certbot webroot 방식.

이 저장소의 Nginx 설정이 소비하는 값

설정 예시 · 인증서 경로관련 템플릿 deploy/nginx/traceback.conf.example 1–32행 · 설명용 발췌 · 원본 행과 일대일로 대응하지 않음 · 원본 파일 열기
server_name api.dev-traceback.com;ssl_certificate /etc/letsencrypt/live/api.dev-traceback.com/fullchain.pem;ssl_certificate_key /etc/letsencrypt/live/api.dev-traceback.com/privkey.pem;proxy_pass http://127.0.0.1:8000;proxy_set_header Host $host;proxy_set_header X-Forwarded-Proto $scheme;

80에서는 ACME 검증 경로를 제공하고 나머지는 HTTPS로 돌립니다. 443에서는 인증서를 제시한 뒤 원래 URL 경로를 Django에 전달합니다. 앱 포트는 EC2 내부 loopback에만 열고, Django의 secure cookie·CSRF가 원래 HTTPS 요청을 알도록 Host와 scheme을 넘깁니다. 전체 파일 보기.

현재 연결이 여기서 멈춥니다: 2026-10-04 외부에서 https://api.dev-traceback.com/_allauth/browser/v1/config의 443 연결이 거부됐습니다. DNS와 보안 그룹은 EC2로 가는 길을 열었지만, EC2의 Nginx에는 아직 443 수신 설정과 인증서가 없습니다. 포트 허용만으로 수신 프로그램이 생기지는 않습니다. 인증서·443 설정 뒤 curl -i https://api.dev-traceback.com/_allauth/browser/v1/config로 공개 경로를 검사합니다. 앱이 아직 배포되지 않았으므로 그때도 200이 보장되지는 않습니다. Vercel rewrite는 적용됐고 현재 인증 경로는 502입니다.
Compose 파일을 왜 두 개 읽나요? 기본 파일은 로컬/공통 앱의 포트와 네트워크를 정의하고, docker-compose_prod.yml은 이미지·운영 보안·health check·DB 제거 설정을 덧씌웁니다. 배포 스크립트가 두 파일을 docker compose -f … -f …로 함께 적용합니다. 따라서 한 파일만 보고 최종 포트가 없다고 판단하면 안 됩니다. 병합된 결과는 docker compose … config로 확인합니다. 이 명령은 env_file의 비밀값도 출력할 수 있으므로 실제 서버 출력은 공개 로그·이슈에 붙이지 않습니다.
아직 필요한 실제 작업: EC2 보안 그룹의 80/443 허용, Nginx HTTP 80, ACME 검증 경로는 확인했습니다. 인증서 발급·갱신, Nginx 443 프록시, 앱의 localhost 8000 실행, 실제 HTTPS 요청 검증이 남았습니다.

앞의 경로를 dev와 prod에 어떻게 적용할지 결정합니다. 서버를 한 대로 시작하는 선택과 환경 분리는 배포 대상과 위험 범위를 바꿉니다.

dev/prod 서버를 어떻게 운영할까요?

저장소의 현재 설계와 GitHub Actions는 dev·prod 각각의 서버와 DB를 기준으로 만들어져 있습니다. 아래 선택지를 눌러 비용과 운영 영향을 비교하세요.

권장: ① 현재 확정 설계대로 진행
개발 중인 서버에는 개발 코드만 배포합니다. 안정화 시 별도 prod EC2·RDS·Vercel 프로젝트를 만들고, 기존 CI/CD가 검증한 이미지 digest를 승격합니다.

① 개발은 개발대로 권장

흐름: 지금은 dev 환경을 완성하고 테스트합니다. 서비스 공개 준비가 되면 독립된 prod 환경을 구축합니다.

  • 기존 feature → development → main 흐름과 CI/CD를 유지
  • 개발 실패가 운영 고객에게 바로 영향 주지 않음
  • 당장은 prod EC2/RDS를 만들지 않아 비용 지출을 미룸
  • prod 구축 후에는 서버·DB 등 운영비가 추가됨

② 기존 dev 인스턴스를 prod로 전환

흐름: 이 서버를 운영 서버로 바꾸고 dev 자동 배포는 멈춥니다.

  • 당장 별도 prod EC2를 만들지 않으므로 인스턴스 비용을 미룸
  • dev에 push할 때 운영 서버가 바뀌지 않게 workflow/환경값을 먼저 바꿔야 함
  • 테스트 공간이 사라져 다시 dev를 만들면 이중 작업
  • RDS와 Vercel 환경 분리도 다시 설계해야 함

지금의 `DEVELOPMENT_INSTANCE_ID` 배포 경로를 그대로 두면 개발 코드가 운영 서버로 갈 수 있어 현재 구조와 맞지 않습니다.

③ 한 EC2에서 dev·prod 같이 실행

흐름: 한 호스트의 별도 Compose stack·환경변수·도메인으로 두 앱을 운영합니다.

  • EC2 한 대 사용으로 호스트 비용을 줄일 수 있음
  • dev/prod별 Docker 포트, Nginx route, DB 접근, 배포 workflow를 직접 분리해야 함
  • 현재 t3.micro의 CPU·메모리와 장애 지점을 공유
  • 호스트 장애나 잘못된 배포가 양쪽 환경에 영향

서버는 한 대라도 DB·자격증명·로그인 도메인은 분리해야 하고, 지금 CI/CD도 수정해야 합니다.

비용 관점: 옵션 ①은 지금 prod 인프라 비용을 시작하지 않는 방법입니다. RDS를 멈춰도 스토리지·백업 비용은 남고, 현재 기록된 생성 추정은 인스턴스와 20 GiB 저장소만 월 USD 20.87입니다. AWS 크레딧은 지출 상한이 아닙니다. S3는 비어 있는 동안 비용이 작지만 요청·저장·전송에 따라 달라질 수 있습니다.

선택한 dev 구성을 실제로 만드는 순서입니다. 위 개념과 상태 지도를 콘솔·터미널 작업에 대응시킵니다.

첫 개발 배포 순서

아래는 추천안 ① 기준입니다. 비용이 생기는 AWS 변경이나 공개 엔드포인트 설정은 각 단계에서 실제 계정과 요금을 확인합니다.

운영 모드를 먼저 정하고 배포 코드를 확인

Dev 서버를 dev 전용으로 유지합니다. 로컬 backend/client 변경을 `development`에 반영할 계획이라면 해당 브랜치 상태와 CI를 확인합니다. 서버에서 저장소를 pull하는 작업은 하지 않습니다.

  • CI quality/test 녹색인지 확인
  • 개발 deployment GitHub Environment 및 AWS OIDC 값 준비
  • main에 직접 배포하거나 dev/prod 인스턴스 ID를 섞지 않기

EC2 실행 기반과 최소 권한 설정

인스턴스 역할에 기존 SSM 권한과 ECR pull 권한이 모두 필요합니다. EC2에 Docker Engine, Compose v2, AWS CLI v2를 준비하고 `/opt/traceback`을 만듭니다.

  • 현재 보안 그룹: 웹 80/443 허용, SSH 22 미개방
  • ECR private repository는 immutable image tag로 준비
  • GitHub OIDC provider와 개발 전용 deploy role 생성; 장기 AWS 키를 GitHub에 넣지 않음
  • RDS는 앱 마이그레이션/테스트 동안만 켜고 종료 후 중지

앱용 DB 사용자와 EC2 비밀값 준비

RDS master password를 앱 런타임에 재사용하지 말고, Django용 DB 사용자·DB를 분리합니다. 비밀값은 로컬 Git 파일이나 Vercel frontend에 두지 않습니다.

  • 각 EC2의 미추적 파일: /opt/traceback/.env, 권한 600
  • dev 설정은 DJANGO_SETTINGS_MODULE=config.settings.development; 현재 코드에서 DEBUG=False
  • TRACEBACK_DATABASE_URL은 private RDS endpoint와 앱 DB 계정 사용
  • FRONTEND_BASE_URL은 Vercel 개발 origin; Django secret, SES, Kakao 값은 환경별 별도 보관
  • 환경변수 이름과 목적은 이 문서의 환경변수 절에서 확인

API 도메인과 reverse proxy 연결

이미 준비한 api.dev-traceback.com의 요청을 EC2 안의 Django 앱까지 전달해야 합니다. 현재 선택은 호스트 Nginx가 TLS/HTTPS를 처리하고 같은 EC2의 Docker 앱으로 proxy하는 방식입니다.

  • Compose 기본 파일의 localhost publish와 운영 오버레이를 함께 배포합니다. 병합된 포트는 127.0.0.1:8000이라 Nginx는 연결할 수 있고 외부 사용자는 직접 접근하지 못합니다.
  • Nginx가 /_allauth, /accounts, /api 요청의 경로를 보존해 upstream으로 전달
  • X-Forwarded-Proto: https와 원래 Host를 Django에 전달해 HTTPS cookie/CSRF 동작을 검증
  • 대안은 Nginx 컨테이너 또는 ALB입니다. 같은 EC2의 Nginx 컨테이너는 배포 방식이 달라지고, ALB는 별도 AWS 서비스와 비용이 추가됩니다.

GitHub Environment와 첫 배포 설정

development Environment와 보호된 development 브랜치는 설정 완료. GitHub가 이 저장소의 OIDC token으로 deploy role을 맡고, SHA-tag 이미지를 ECR에 push한 뒤 DEVELOPMENT_INSTANCE_ID로 지정한 EC2에 SSM 명령을 보냅니다.

  • AWS_REGION=ap-northeast-2 · 리전
  • ECR_REPOSITORY=traceback · private image repository
  • AWS_DEPLOY_ROLE_ARN=arn:aws:iam::968579693658:role/traceback-development-deploy · OIDC로 맡는 IAM role 주소
  • DEVELOPMENT_INSTANCE_ID=i-051f85a1ac4e64a2c · 배포 명령 대상 EC2

.env.dev.git은 기록용입니다. GitHub가 자동으로 읽지 않으므로 저장소 Settings → Environments → development에 별도로 입력합니다. 정적 Access Key는 등록하지 않았습니다.

서버 배포 뒤 Vercel 환경별 연결

client repo의 vercel.ts는 DJANGO_ORIGIN 하나를 읽어 rewrite를 구성합니다. 2026-10-03 콘솔에서 Production 범위에 변수를 저장했습니다. Production Branch가 development인 이 개발 전용 프로젝트에서는 이 범위가 개발 프런트 배포에 적용됩니다.

  • Production scope: DJANGO_ORIGIN=https://api.dev-traceback.com 등록 완료. 2026-10-04 재배포로 값이 적용됐습니다. 현재 API HTTPS 연결이 거부되어 인증 경로는 502입니다.
  • Preview scope: 다른 브랜치와 PR 미리보기 배포에 적용됩니다. Preview URL의 CSRF trusted origins와 Kakao callback 정책을 정하기 전에는 비워 둡니다.
  • Development scope: vercel dev 및 Vercel CLI가 값을 가져오는 로컬 개발용입니다. 일반 로컬 Vite 개발 서버는 client의 로컬 proxy를 쓰므로 여기에 자동 적용되지 않습니다.
  • .env.dev는 로컬 파일이며 Vercel에 자동 업로드되지 않습니다. Vercel Dashboard에 등록한 값과 별개로 관리합니다.
  • DB 비밀번호, Django secret, SES, Kakao secret은 Vercel에 넣지 않습니다. 현재 vercel.ts가 소비하는 값은 공개 HTTPS origin인 DJANGO_ORIGIN뿐입니다.
  • API HTTPS 연결 뒤 /_allauth, /accounts, /api rewrite와 cookie/CSRF/Kakao callback을 브라우저에서 검증

외부에서 인증·DB·메일을 검증하고 끄기

개발용 Vercel 주소에서 설정 endpoint, 이메일 가입/인증, 로그인/로그아웃, CSRF 변경 요청, Kakao callback과 계정 연결 해제를 확인합니다.

  • Vercel에서 /_allauth/browser/v1/config가 200으로 오고 Django에서 DB 응답
  • HTTPS cookie, proxy host/protocol, Django allowed hosts와 CSRF 동작 확인
  • 외부 HTTP/HTTPS에서 앱만 노출되는지 확인; RDS는 계속 private
  • 메일 발송을 실사용 테스트할 계획이면 SES production access와 verified sender/domain도 확인
  • RDS는 테스트 종료 후 중지. S3 업로드 IAM은 기능이 생길 때만 최소 prefix 권한으로 추가

설정 중 낯선 단어가 나오면 이 용어집으로 돌아오세요. 앞의 흐름을 다시 읽을 때 필요한 네트워크·AWS 말을 정리합니다.

처음 나오는 네트워크 용어

위의 요청·배포 그림에서 낯선 단어를 다시 찾는 참고용입니다. 단어가 서로 어디에 놓이고 무엇을 결정하는지는 VPC·서브넷·경로·권한 구조도와 이 문서의 네트워크 점검 그림을 함께 보세요.

일반 네트워크 용어

HTTP · HTTPS
HTTP는 웹 요청·응답 형식이고 HTTPS는 그 통신을 TLS로 암호화한 방식입니다. 보통 80/443 포트를 사용합니다.
TLS 인증서 · 개인 키
인증서는 접속한 도메인의 서버 신원을 증명하고 암호화 연결을 돕습니다. 대응하는 개인 키는 서버에서 보호하며 공개 저장소에 넣지 않습니다.
CA · ACME
CA는 인증서를 발급하는 기관, ACME는 도메인 확인과 발급·갱신을 자동화하는 규약입니다. Let's Encrypt와 Certbot은 각각 CA와 ACME client의 예입니다.
Reverse proxy · 역방향 프록시
사용자 요청을 먼저 받은 뒤 내부 앱 서버로 대신 전달하는 서버입니다. 이 구성에서는 Nginx가 해당 역할을 합니다.
Upstream · 전달 대상
프록시가 요청을 넘기는 다음 서버입니다. 여기서는 Django 앱의 127.0.0.1:8000입니다.
Loopback · 자기 자신 주소
127.0.0.1은 해당 컴퓨터 자신을 가리킵니다. EC2 안의 Nginx와 앱 사이에서만 포트를 열 때 씁니다.
TLS 종료
HTTPS 암호화를 풀고 인증서를 제시하는 지점입니다. 현재 계획에서는 EC2의 Nginx가 처리합니다.
인바운드 / 아웃바운드
보안 경계로 들어오는 연결 / 그 경계에서 밖으로 나가는 연결입니다. 인터넷의 443 요청은 인바운드이고, EC2가 RDS 5432로 접속하는 것은 아웃바운드입니다.

AWS 및 Docker 용어

Security Group · 보안 그룹
EC2나 RDS의 가상 방화벽 규칙입니다. 포트와 허용할 출발지/대상을 지정합니다.
ALB Listener · 수신기
ALB가 어떤 포트/프로토콜(예: HTTPS 443)을 받을지 정의합니다.
Target group · 대상 그룹
ALB가 요청을 전달할 앱 서버 묶음과 상태 확인 규칙입니다.
Health check · 상태 확인
앱이 요청을 처리할 수 있는지 주기적으로 검사해 정상 대상을 고르는 절차입니다.
Compose overlay · 설정 덧씌우기
여러 Compose 파일을 순서대로 합쳐 환경별 최종 구성을 만듭니다. 뒤 파일은 앞 설정을 추가하거나 바꿀 수 있습니다.

서버와 배포 흐름을 구분했으니 각 실행 장소가 읽는 환경변수를 나눕니다. 한곳에 저장한 값이 다른 곳으로 자동 전파되지는 않습니다.

환경변수는 저장 위치마다 목적이 달라요

같은 값 이름이 있더라도 어디에 넣는지와 누가 읽는지 구분합니다. 절대 secret 값을 이 문서나 Git에 적지 않습니다.

GitHub Environment에 값을 넣으면 EC2의 .env도 자동으로 채워지나요?

아니요. GitHub 변수는 workflow가 배포 중 읽는 값이고, EC2의 /opt/traceback/.env는 실행 중인 Django 컨테이너가 읽는 값입니다. 서로 다른 컴퓨터와 시점에 존재합니다. 이 저장소의 배포 스크립트는 EC2 환경 파일의 존재를 검사하며 비밀값을 GitHub에서 복사해 만들지 않습니다. Vercel의 DJANGO_ORIGIN도 별도의 Vercel 설정이며 새 배포 후 확인해야 합니다.

Git 브랜치 이름과 Vercel 환경 이름은 서로 다른 축입니다

Git development 브랜치→이 프로젝트의 Production Branch→Vercel Production 배포→Production 범위 DJANGO_ORIGIN
미래의 Git main 브랜치→별도 운영 Vercel 프로젝트→그 프로젝트의 Production 범위 DJANGO_ORIGIN

일반적인 단일 프로젝트 구성은 main을 Production Branch로 두고, development 배포에는 Preview 범위 또는 브랜치별 Preview 값을 씁니다. 별도 개발·운영 프로젝트 구성에서는 각 프로젝트가 자기 Production Branch와 Production 변수를 갖습니다. TRACEBACK은 후자를 선택했고 현재는 개발 프로젝트만 존재합니다. Vercel Development 범위는 두 구성 모두 로컬 개발용입니다. Vercel 브랜치 배포 · 환경변수 범위

코드를 서버에 전달하는 두 방식

방식 A · Git 저장소→EC2 git pull→checkout에서 빌드·실행
방식 B · CI 이미지→ECR에 게시→EC2가 이미지 pull·실행

A · checkout 안에 .env

서버에서 저장소를 읽고 Compose·소스·미추적 .env를 한 폴더에 둘 수 있습니다. 수동 작업을 눈으로 따라가기 쉽습니다. 서버에 Git 접근과 빌드 도구가 필요하고, checkout의 브랜치·로컬 변경 상태를 관리해야 합니다. .env를 실수로 추적하거나 정리 명령으로 지우지 않도록 관리합니다.

B · 이미지 + 실행 폴더의 .env

CI가 한 번 빌드한 이미지를 서버가 받아 실행합니다. 서버에 Git 접근이나 소스 빌드가 필요 없고 같은 image digest를 다른 환경으로 승격할 수 있습니다. 대신 CI·ECR을 먼저 구성하고, 서버에는 Compose 파일과 추적하지 않는 .env를 준비해야 합니다. TRACEBACK은 이 방식이며 실행 폴더로 /opt/traceback을 선택했습니다.

환경 파일의 위치는 별도 선택입니다. A에서도 checkout 밖의 파일을 가리킬 수 있고, B에서도 실행 폴더 안의 파일을 사용할 수 있습니다. 어느 쪽이든 Git에 비밀값을 커밋하지 않고 서버에서 접근 권한을 제한합니다. Docker Compose의 env_file이 앱 컨테이너로 값을 전달합니다. Docker Compose 공식 설명

왜 EC2에서 git pull하지 않고 /opt/traceback/.env를 만드나요?

일반적인 배포에는 서버가 Git 저장소를 pull해 빌드하는 방식과, CI가 이미지를 빌드해 서버가 그 이미지만 pull하는 방식이 모두 있습니다. TRACEBACK은 후자를 선택했습니다. GitHub Actions가 이미지를 ECR에 올리고, EC2는 이미지를 내려받습니다. /opt/traceback은 실행용 Compose 파일과 서버 설정을 모으려고 우리가 정한 경로이며 Git checkout이 아닙니다. 배포 스크립트가 이미지 안에서 Compose 파일 두 개를 이 디렉터리로 꺼냅니다. 스크립트는 그곳으로 이동해 docker compose --env-file .env를 실행하고, Compose 파일의 env_file: .env가 서버 전용 값을 앱 컨테이너에 전달합니다. /opt는 Docker나 ECR의 필수 경로가 아닙니다. Linux의 일반 디렉터리 관례에서는 추가 앱에 /opt, 서비스 데이터에 /srv, 호스트 설정에 /etc 계열도 사용합니다. 현재처럼 한 디렉터리에 Compose와 비밀값을 함께 두는 것은 단순한 초기 운영 선택이며, 경로를 바꾸려면 스크립트·Compose의 파일 경로·서버 파일을 함께 바꾸면 됩니다. 배포 스크립트 · Compose 설정 · Linux FHS /opt

SSM으로 들어왔는데 왜 /opt/traceback에 못 들어가나요?

현재 실행 폴더는 root 전용이고, Session Manager 셸 사용자는 ssm-user입니다. AWS의 ssm:StartSession 권한과 Linux 디렉터리의 소유자·그룹·실행(x) 권한은 별개입니다. 비밀 .env를 지키려는 선택이며, id와 ls -ld /opt/traceback으로 실제 권한을 확인합니다. 관리 권한이 있으면 sudo -i 뒤에 이동하고 작업 후 exit합니다. root 전용 폴더와 전용 배포 그룹의 장단점은 1번 접속 가이드에 있습니다.

인증 메일도 이 서버에서 나갑니다. 세션·allauth 선택과 SMTP·SES 발송 흐름을 먼저 보면 FRONTEND_BASE_URL과 SES 비밀값을 왜 EC2에 두는지 이해할 수 있습니다. 로컬은 콘솔 메일러, AWS는 SES SMTP, Vercel은 인증 요청을 전달하는 프런트입니다.

Django가 os.environ에서 값을 읽습니다. DJANGO_SETTINGS_MODULE은 실행할 settings 모듈을 고릅니다. production settings는 시작 시 TRACEBACK_DATABASE_URL이 없으면 실패하게 해 잘못된 기본 DB로 뜨지 않도록 합니다. 메일과 Kakao 값도 같은 settings 파일에서 읽습니다.

왜 이렇게 골랐나: 한 EC2와 Compose 하나로 시작하는 동안 서버의 권한 600인 미추적 .env가 가장 단순하고 배포 코드에 비밀값이 들어가지 않습니다. 대안은 systemd 환경 파일이나 AWS Systems Manager Parameter Store/Secrets Manager에서 실행 시 주입하는 방식입니다. 서버 수가 늘거나 회전·감사가 중요해지면 관리형 저장소로 옮길 수 있습니다. CI는 비밀 없는 fixture를 따로 써서 AWS 값을 CI에 복사하지 않습니다. DATABASE_URL 대신 프로젝트가 명시적으로 요구하는 TRACEBACK_DATABASE_URL만 씁니다.
GitHub Variables와 Secrets: Workflow는 vars.AWS_REGION, vars.ECR_REPOSITORY, vars.AWS_DEPLOY_ROLE_ARN, vars.DEVELOPMENT_INSTANCE_ID를 development Environment에서 읽습니다. 앞의 role ARN은 OIDC 인증 이후 맡을 역할을 지정하고, instance ID는 작업할 EC2를 고릅니다. 장기 AWS Access Key는 넣지 않고 OIDC로 짧은 권한을 받습니다. DB 암호 같은 런타임 비밀값은 GitHub에 전달하지 않고 EC2 앱 환경에 따로 둡니다.

AWS Secrets Manager / SSM Parameter Store

AWS에서 중앙 저장하고 IAM 권한으로 읽을 수 있습니다. 여러 서버, 감사, 자동 회전이 중요해지면 검토합니다. 저장 요금/KMS 설정과 앱 또는 배포 코드의 조회 경로가 추가되며, 현재는 선택하지 않았습니다.

비용과 안전 기준

초기 고정비 줄이기

  • 당장은 EC2 1대, Single-AZ RDS, NAT Gateway 없음, ALB 없음
  • RDS는 개발/테스트 때 켜고 끝난 뒤 중지. 중지 중에도 storage/backup 요금이 남음
  • EC2 stop은 시간 비용을 줄일 수 있지만 public IPv4가 바뀔 수 있어 DNS와 TLS origin에 영향
  • 현재 문서의 RDS 생성 추정 USD 20.87/월은 RDS instance + 20 GiB storage만이며 나머지 요금은 별도
  • ECR repository 자체는 월 정액이 아니고 이미지 저장량·인터넷 전송에 따라 과금; 빈 repo에는 저장 이미지 비용 없음
  • AWS credit은 bill cap이 아님. 실제 Billing과 Budget alert를 확인

인터넷에 내보내기 전에

  • Django DEBUG=False; secret/key는 EC2 파일에만 보관
  • RDS internet access 비활성, 5432 source는 개발 EC2 security group만 허용 — 현재 설정 확인됨
  • EC2 inbound 80/443은 전 세계에서 접근 가능하고 22는 닫힘 — 현재 설정 확인됨
  • EC2 outbound는 전체 IPv4 허용 — 동작은 하지만 최소 권한은 아님; 사용처 검증 뒤 제한 여부 결정
  • 기본 VPC route table의 IGW 경로는 확인됨; network ACL 규칙은 추가 확인 필요
  • Vercel 개발 프로젝트의 Production 범위 DJANGO_ORIGIN은 적용·재배포됨. API HTTPS 준비 후 인증 검증; Preview 범위는 CSRF·OAuth 정책 결정 후
  • Nginx HTTP·ECR pull IAM은 확인됨. TLS, 443 프록시, 런타임 .env, 앱 전용 RDS 사용자 준비
  • DB migration 전에 RDS backup/restore 지점 확인
