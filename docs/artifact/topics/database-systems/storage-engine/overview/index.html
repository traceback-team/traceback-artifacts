Database Engine이란 무엇인가?

엔진은 어디에서
무엇을 할까?

먼저 Database Engine이라는 넓은 용어와 공통 계층 지도를 봅니다. 그다음 PostgreSQL·MySQL/InnoDB·SQLite·RocksDB가 각각 DBMS인지 Engine인지, 어떤 형태로 결합되는지 구분합니다.

페이지 전체에서 사용할 하나의 예제
UPDATE accounts
SET balance = balance - 100
WHERE id = 7;

뜻: accounts 테이블에서 id가 7인 한 기록을 찾아 balance를 100 줄입니다.

학습 범위 · 특정 TRACEBACK 배포 상태가 아닌 일반 개념입니다. 먼저 넓은 Database Engine 용어와 공통 저장 계층을 이해하고, 이어서 네 제품의 역할과 결합 형태를 구분합니다. SQL 처리 단계와 제품 내부 자료구조는 다음 엔진 학습 페이지에서 다룹니다.

정의

Engine은 시스템의 핵심 기능을 실제로 수행하는 구현체를 가리키지만, 그 기능 범위가 고정된 공식 계층은 아닙니다. 제품과 문맥에 따라 저장 기능만 뜻하기도 하고 SQL 처리부터 저장까지 넓게 뜻하기도 합니다. Storage Engine은 그중 데이터의 저장·탐색·변경을 중심으로 맡으며, 트랜잭션·복구까지 포함하는지는 구현마다 다릅니다. 따라서 이름보다 어느 기능과 논리 계층을 구현하는지 확인해야 합니다.

Layer · 논리적 역할시스템 안에서 무엇을 담당하는가
Engine · 핵심 구현체문맥상 핵심 기능을 실제 코드로 수행하는가
Library · 제공 형태다른 프로그램이 링크·호출해 사용하는가
개념적 위치 지도요청을 받는 계층과 실제 저장 자원을 한 장에 표시

디스크 기반 서버형 관계형 DBMS를 단순화한 공통 그림입니다. 모든 데이터 제품이 이 구조를 그대로 따르는 것은 아닙니다. 제품이 SQL을 제공하는지, 저장 기능만 제공하는지, 별도 Server인지 내장 Library인지는 다음 Step에서 구분합니다.

DBMS 내부 관련 기능: Buffer, 복구 Log, MVCC, Lock, Transaction은 요청이 차례로 통과하는 별도 단계가 아닙니다. 구현에 따라 여러 내부 Module이 나누어 맡거나 하나의 저장 구성요소 안에 묶일 수 있습니다.
OS 경계: 저장 계층이 물리 장치를 항상 직접 제어하는 것은 아닙니다. 일반적으로 파일·블록 I/O는 운영체제와 파일시스템을 통합니다.

이제부터: 서버형 관계형 DBMS의 대표 요청 흐름위 레이어 지도에서 SQL 요청 하나가 내려갔다가 결과로 돌아오는 과정을 확대합니다.

처음 나온 용어 자세히 보기
  • Record/Row: 테이블의 한 기록. 여기서는 id=7 계좌입니다.
  • Index: 모든 기록을 읽지 않고 대상을 빨리 찾는 탐색 구조입니다.
  • Page: DBMS가 메모리와 파일 사이에서 데이터를 다루는 일정 크기의 블록입니다.
  • Buffer: Page를 메모리에 보관해 읽기와 변경에 사용하는 영역입니다.
  • Interface: 두 내부 구성요소가 서로 호출하는 약속입니다.
  • Library와 Engine: Engine은 문맥상 핵심 기능을 수행하는 구현체이고, Library는 다른 프로그램이 링크·호출하는 코드 제공·결합 형태입니다. 서로 다른 분류 기준이므로 하나의 구현이 Library이면서 Storage Engine일 수도 있습니다.

저장 구현 경계만 제공 · 호출자가 Key–Value API를 직접 사용합니다.

기능 분류와 실행·제공 형태는 서로 다른 기준입니다. PostgreSQL·MySQL·SQLite는 SQL과 트랜잭션을 제공하는 DBMS이고, RocksDB는 SQL이 없는 Key–Value Storage Engine Library입니다. Server는 별도 프로세스로 요청을 받는 실행 형태, Library는 호출자가 불러 쓰는 제공 형태입니다.

따라서 PostgreSQL은 SQL Core와 저장 책임이 한 제품 안에 통합된 서버형 DBMS, MySQL은 Server가 Handler API로 InnoDB 같은 테이블 엔진을 선택하는 서버형 DBMS, SQLite는 앱에 Library로 내장되는 완전한 DBMS, RocksDB는 상위 시스템이 조합하는 저장 부품입니다.

추가 사례 5개 보기 · MyISAM · XtraDB · Aria · Berkeley DB · LevelDB
Server DBMS가 저장 책임을 맡기는 Engine 계열상위 Server가 SQL을 처리하고 Engine이 Table 저장을 담당
MyISAMMySQL 8.4

MySQL에서 Table별로 선택할 수 있는 비트랜잭션 Storage Engine입니다. 현재 기본값은 InnoDB이며 MyISAM은 명시적으로 선택합니다.

결합: MySQL Server → Handler API → MyISAM
AriaMariaDB

MariaDB에 포함된 Storage Engine으로, MyISAM의 더 현대적인 대안이자 Crash-safe 사용을 고려한 구현입니다.

결합: MariaDB Server → Storage Engine API → Aria
XtraDB역사적 사례

InnoDB를 확장한 호환 계열 Engine입니다. 과거 MariaDB의 기본 Engine이었지만 현재 MariaDB에서는 더 이상 제공되지 않습니다.

의미: “Server가 끼워 쓰는 InnoDB 계열 구현”의 역사적 사례
애플리케이션이 직접 포함하는 Key–Value 저장 Library 계열SQL Parser·Planner 없이 Library API로 직접 호출
Berkeley DBEmbedded

애플리케이션에 링크되는 범용 Embedded Database Engine입니다. Key와 Value를 불투명한 Record로 저장하며 SQL Server를 자체 제공하지 않습니다.

결합: Application → Berkeley DB Library → File
LevelDBEmbedded

정렬된 String Key→Value Mapping을 제공하는 저장 Library입니다. 호출자가 Put·Get·Delete API를 직접 사용합니다.

결합: Application → LevelDB Library → SSTable Files

같은 “Engine”이라는 이름이어도 결합 위치가 다릅니다. MyISAM·Aria·XtraDB는 Server DBMS 아래의 Table Engine 문맥이고, Berkeley DB·LevelDB·RocksDB는 애플리케이션이 직접 포함할 수 있는 저장 Library 문맥입니다.

이 구분이 다음 페이지에 필요한 이유 · Parser부터 Executor까지의 SQL 처리 과정은 PostgreSQL·MySQL 같은 DBMS가 맡습니다. RocksDB는 그 전체 과정을 제공하지 않으며, MySQL에서는 실행 중 저장 책임이 Handler API 아래 InnoDB로 넘어갑니다.
