어떻게 다를까?

둘 다 SQL을 처리하고 데이터를 안전하게 저장하지만 내부 책임을 묶는 방식은 다릅니다. 같은 UPDATE를 Parser부터 Executor까지 따라간 뒤, SQL Core 아래의 저장 접근 경계와 메모리·MVCC·복구 로그의 위치를 비교합니다.

POSTGRESQL 18통합형 Server DBMS

SQL Core와 공용 저장 기능이 한 PostgreSQL 제품 안에 있습니다. MySQL의 InnoDB처럼 하나의 이름 붙은 Engine 상자가 전체 저장 책임을 감싸지는 않습니다.

MYSQL 8.4 + INNODBServer + 선택 가능한 Engine

MySQL Server가 SQL 공통 계층을 맡고 Handler API를 통해 기본 Storage Engine인 InnoDB에 Table 저장을 위임합니다.

학습 범위 · 일반적인 PostgreSQL 18의 기본 Heap Table과 B-tree Index, MySQL 8.4의 InnoDB Table을 비교합니다. 특정 TRACEBACK 배포 상태가 아니며, SQLite·RocksDB·레거시 MySQL Engine의 내부 구조는 이 페이지에서 다루지 않습니다.

SQL의 의미가 실행과 저장으로 이어지는 과정

먼저 SQL이 내부 표현으로 바뀌는 과정을 보고, 그 실행이 PostgreSQL과 MySQL/InnoDB의 저장 경계로 어떻게 이어지는지 확인하세요.

Step 1 · SQL transformation

SQL은 단계마다 다른 내부 표현으로 바뀝니다

공통 역할 · 이름은 제품별 차이

이 단계의 범위 · 같은 UPDATE 예제를 사용하지만, 아래 제품 탭에 따라 실제 단계명·단계 수·내부 표현이 함께 바뀝니다. 저장 시스템 호출은 Executor/Execution이 수행 중 사용하는 경계이고, 완료 응답은 실행 뒤 프로토콜 계층이 전송하므로 별도의 SQL 처리 단계로 세지 않습니다.

PostgreSQL 18: Tree는 모두 같지 않습니다. 아래에서 각 Tree가 무엇을 표현하는지 먼저 구분한 뒤 단계를 선택하세요.

PostgreSQL도 교체 가능한 부분이 있나?

Table/Index Access Method 확장 지점은 있지만 MySQL처럼 Table마다 InnoDB·MyISAM을 고르는 동일한 Engine Model은 아닙니다.

MySQL과 InnoDB는 별도 Server인가?

논리적 책임은 분리되지만 일반적인 구성에서는 같은 mysqld Process 안에서 동작합니다.

Engine이라는 말이 왜 헷갈리나?

제품 전체의 핵심 구현을 넓게 부르기도 하고, MySQL Storage Engine처럼 공식 구성요소 이름으로도 쓰기 때문입니다.

PostgreSQL Access Method와 MySQL Storage Engine 정확히 구분하기
  • PostgreSQL Table Access Method: Table 저장 방식을 Core와 연결하는 Callback API입니다. 기본 구현은 Heap이며 pg_am Catalog에 등록됩니다.
  • PostgreSQL Index Access Method: B-tree·Hash·GiST·GIN·SP-GiST·BRIN처럼 Index Type별 동작을 Core에 제공합니다.
  • MySQL Storage Engine: Table의 실제 저장·검색·Transaction 기능을 Handler 경계 아래에서 구현합니다. MySQL 8.4의 기본 범용 Engine은 InnoDB입니다.
02 · one UPDATE

id=7의 balance를 줄일 때 데이터는 어디를 지날까?

같은 SQL · 제품별 경로

UPDATE accounts SET balance = balance - 100 WHERE id = 7;을 계속 사용합니다. 아래는 id에 B-tree Index가 있고 Index Scan/Lookup이 선택되었다는 학습용 가정입니다.

PostgreSQL: Index와 Heap Table이 별도 Relation이고, Index가 반환한 TID로 Heap Tuple을 찾습니다.

01 · PLANModifyTable + Index Scan

Executor가 Plan Tree를 따라 UPDATE를 시작합니다.

02 · INDEX AMB-tree에서 id=7 탐색

Index Entry가 대상 Heap Tuple의 TID를 알려 줍니다.

03 · TABLE AMHeap Tuple 접근

Heap의 Block·Item 위치에서 현재 Row Version을 읽습니다.

04 · SHARED SERVICES새 Tuple Version + WAL

MVCC용 새 Version, Dirty Page와 WAL Record를 만듭니다.

05 · RESULTUPDATE 1

완료 상태가 Protocol 계층을 통해 Client로 돌아갑니다.

핵심: PostgreSQL Index는 Row 자체를 품은 Clustered Index가 아니라 Heap Tuple의 위치(TID)를 가리킵니다. HOT 적용 여부와 Index 변경 필요성은 변경 Column과 Page 조건에 따라 달라집니다.

Tuple Version·WAL·Data Page Flush 구분하기
UPDATE는 일반적으로 새 Tuple Version을 만들고 이전 Version은 MVCC 가시성 규칙에 따라 남습니다. WAL은 Crash Recovery 기록이고, Shared Buffer의 Dirty Page가 Data File에 즉시 Flush되었다는 뜻은 아닙니다.

MySQL/InnoDB: id가 Primary Key라고 가정하면 Clustered Index 탐색이 Row Data로 바로 이어집니다.

01 · QEPUPDATE Access Path

MySQL Server Execution이 Query Execution Plan을 시작합니다.

02 · BOUNDARYHandler API 호출

Server가 InnoDB에 id=7 Row 탐색과 변경을 요청합니다.

03 · INNODB INDEXClustered Index Lookup

Primary Key Leaf Record가 Row Data를 함께 담습니다.

04 · INNODB TXUndo + Redo + Dirty Page

이전 Version과 복구 기록을 만들고 Buffer Pool Page를 변경합니다.

05 · RESULTOK · affected rows

성공 상태가 MySQL Protocol을 통해 Client로 돌아갑니다.

핵심: InnoDB Buffer Pool·MVCC·Lock·Undo·Redo는 Handler 아래 InnoDB 경계 안에 모여 있습니다. Secondary Index를 쓰면 Primary Key로 Clustered Index를 다시 찾을 수 있습니다.

Undo·Redo·Data Page Flush 구분하기
Undo는 Rollback과 Consistent Read용 이전 Version을 제공하고, Redo는 Crash Recovery에서 변경을 재실행하는 기록입니다. Buffer Pool Dirty Page는 나중에 Tablespace로 Flush될 수 있습니다.
03 · memory, versions & recovery

같은 기능이 어느 경계 안에 들어 있을까?

책임 위치 비교

기능 이름이 비슷해도 소유 경계와 자료구조는 다릅니다. PostgreSQL은 공용 Server Module들이 책임을 나누고, MySQL에서는 많은 저장 책임이 InnoDB 안에 모입니다.

POSTGRESQL 18 · SHARED MODULES

한 Engine 상자가 아니라 공용 구성요소의 협력

Memory

Shared Buffer Manager가 Table·Index Page를 PostgreSQL 전체에서 관리합니다.

Row Version

Heap Tuple Header의 Transaction 정보와 Snapshot/Visibility 규칙이 MVCC를 구성합니다.

Index → Row

Secondary Index Entry가 TID로 별도 Heap Relation의 Tuple Version을 가리킵니다.

Recovery

WAL과 Checkpoint가 Crash Recovery와 물리 Page 반영 경계를 이룹니다.

Files

Heap Relation, Index Relation, FSM/VM Fork, WAL Segment가 목적별로 나뉩니다.

≠
일대일 대응 아님
MYSQL 8.4 · INNODB ENGINE

저장·Transaction 기능이 InnoDB 경계 안에 결집

Memory

InnoDB Buffer Pool이 InnoDB Table·Index Page를 Cache합니다.

Row Version

Clustered Record의 Transaction Field와 Undo가 이전 Version과 Consistent Read를 지원합니다.

Index → Row

Primary Key Clustered Index Leaf가 Row Data를 담고 Secondary Index는 Primary Key를 담습니다.

Recovery

InnoDB Redo Log와 Checkpoint가 Crash Recovery와 Tablespace 반영 경계를 이룹니다.

Files

Tablespace, Redo Log, Undo Tablespace 등 InnoDB 관리 File이 목적별로 나뉩니다.

비교 기준: PostgreSQL WAL과 InnoDB Redo, 오래된 Heap Tuple과 InnoDB Undo는 목적이 일부 대응하지만 구현과 소유 경계가 같지는 않습니다. “누가 Page를 Cache하고, 이전 Version을 어디에 두며, 복구 기록을 누가 관리하는가”를 보세요.

이 페이지에서 의도적으로 다루지 않은 내부 세부사항
PostgreSQL TOAST·Vacuum·HOT 세부 조건, InnoDB Change Buffer·Adaptive Hash Index·Purge·Doublewrite, 각 제품의 Lock Mode와 Isolation Level은 별도 학습 주제입니다. 여기서는 가장 큰 책임 경계와 기본 저장 경로만 비교합니다.
