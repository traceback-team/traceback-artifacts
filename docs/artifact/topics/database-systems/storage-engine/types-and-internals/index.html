둘 다 SQL을 처리하고 데이터를 안전하게 저장하지만 내부 책임을 묶는 방식은 다릅니다. 같은 UPDATE를 Parser부터 Executor까지 따라간 뒤, SQL Core 아래의 저장 접근 경계와 메모리·MVCC·복구 로그의 위치를 비교합니다.

POSTGRESQL 18통합형 Server DBMS

SQL Core와 공용 저장 기능이 한 PostgreSQL 제품 안에 있습니다. MySQL의 InnoDB처럼 하나의 이름 붙은 Engine 상자가 전체 저장 책임을 감싸지는 않습니다.

MYSQL 8.4 + INNODBServer + 선택 가능한 Engine

MySQL Server가 SQL 공통 계층을 맡고 Handler API를 통해 기본 Storage Engine인 InnoDB에 Table 저장을 위임합니다.

학습 범위 · 일반적인 PostgreSQL 18의 기본 Heap Table과 B-tree Index, MySQL 8.4의 InnoDB Table을 비교합니다. 특정 TRACEBACK 배포 상태가 아니며, SQLite·RocksDB·레거시 MySQL Engine의 내부 구조는 이 페이지에서 다루지 않습니다.

SQL의 의미가 실행과 저장으로 이어지는 과정

먼저 SQL이 내부 표현으로 바뀌는 과정을 보고, 그 실행이 PostgreSQL과 MySQL/InnoDB의 저장 경계로 어떻게 이어지는지 확인하세요.

Step 1 · SQL transformation

먼저 분리할 개념

AST는 “Tree처럼 보이는 모든 내부 구조”의 이름이 아닙니다

AST는 SQL 문법의 핵심 관계를 Node로 표현한 문법 자료구조입니다. Query Tree·Path·Plan Tree도 Node가 연결된 형태지만 각각 의미·후보·실행 방법을 담으므로 AST라고 부르지 않습니다.

왜 Tree인가? UPDATE 아래에 대상 Table, SET 항목, WHERE 조건이 중첩되기 때문입니다. 메모리에는 그림 선이 저장되는 것이 아니라 C/C++ 객체와 Pointer·List가 저장되고, Pointer를 따라가면 부모→자식 관계가 Tree 모양이 됩니다. 항상 Binary Tree인 것도 아닙니다.

03 · memory, versions & recovery

같은 기능이 어느 경계 안에 들어 있을까?

책임 위치 비교

기능 이름이 비슷해도 소유 경계와 자료구조는 다릅니다. PostgreSQL은 공용 Server Module들이 책임을 나누고, MySQL에서는 많은 저장 책임이 InnoDB 안에 모입니다.

POSTGRESQL 18 · SHARED MODULES

한 Engine 상자가 아니라 공용 구성요소의 협력

Memory

Shared Buffer Manager가 Table·Index Page를 PostgreSQL 전체에서 관리합니다.

Row Version

Heap Tuple Header의 Transaction 정보와 Snapshot/Visibility 규칙이 MVCC를 구성합니다.

Index → Row

Secondary Index Entry가 TID로 별도 Heap Relation의 Tuple Version을 가리킵니다.

Recovery

WAL과 Checkpoint가 Crash Recovery와 물리 Page 반영 경계를 이룹니다.

Files

Heap Relation, Index Relation, FSM/VM Fork, WAL Segment가 목적별로 나뉩니다.

≠
일대일 대응 아님
MYSQL 8.4 · INNODB ENGINE

저장·Transaction 기능이 InnoDB 경계 안에 결집

Memory

InnoDB Buffer Pool이 InnoDB Table·Index Page를 Cache합니다.

Row Version

Clustered Record의 Transaction Field와 Undo가 이전 Version과 Consistent Read를 지원합니다.

Index → Row

Primary Key Clustered Index Leaf가 Row Data를 담고 Secondary Index는 Primary Key를 담습니다.

Recovery

InnoDB Redo Log와 Checkpoint가 Crash Recovery와 Tablespace 반영 경계를 이룹니다.

Files

Tablespace, Redo Log, Undo Tablespace 등 InnoDB 관리 File이 목적별로 나뉩니다.

비교 기준: PostgreSQL WAL과 InnoDB Redo, 오래된 Heap Tuple과 InnoDB Undo는 목적이 일부 대응하지만 구현과 소유 경계가 같지는 않습니다. “누가 Page를 Cache하고, 이전 Version을 어디에 두며, 복구 기록을 누가 관리하는가”를 보세요.

이 페이지에서 의도적으로 다루지 않은 내부 세부사항
PostgreSQL TOAST·Vacuum·HOT 세부 조건, InnoDB Change Buffer·Adaptive Hash Index·Purge·Doublewrite, 각 제품의 Lock Mode와 Isolation Level은 별도 학습 주제입니다. 여기서는 가장 큰 책임 경계와 기본 저장 경로만 비교합니다.
