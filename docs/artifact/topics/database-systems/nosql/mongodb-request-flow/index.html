02 · BSON

객체는 Network에서 어떤 모습일까?

BSON과 Wire protocol은 같은 말이 아닙니다. BSON은 Document 표현 형식이고, Wire protocol은 그 BSON을 담아 주고받는 message 규칙입니다.

별도 직렬화 실험 · 주문 DOCUMENT
{ _id: 1001,
  customerId: 7,
  status: "PAID",
  items: [ ... ], total: 37000 }
→
DRIVER · BSON BYTES
ed000000 10 5f696400 e9030000
10 637573746f6d65724964 ...

전체 길이: 237 bytes

구분: 위 237 B는 Lab에서 BSON.serialize(order)로 주문 Document 전체를 직렬화한 결과입니다. 앞의 find 요청은 주문 전체가 아니라 Command와 Filter를 BSON으로 보냅니다.

BSON: 길이와 Type 정보가 들어 있는 Binary Document 형식. OP_MSG: 현대 MongoDB 요청·응답의 표준 Wire message 형식. OP_MSG body section에 BSON command object가 들어갑니다.

03 · QUERY

mongod는 요청을 어떻게 실행으로 바꿀까?

“MongoDB frontend”는 별도 process 이름이 아니라 mongod 안의 network·command·query 책임을 묶어 설명한 개념 경계입니다.

짧은 답: Query Planner는 요청의 의미를 바꾸지 않고, 같은 결과를 만들 수 있는 후보 경로 중 하나를 선택합니다. 아래에서는 실제로 관찰한 주문 조회 한 건을 끝까지 따라갑니다.

APPLICATION · DRIVER APIorders.find({ customerId: 7, status: "PAID" })
→
DRIVER · 개념적 COMMAND BODY{ find: "orders", filter: { customerId: 7, status: "PAID" }, $db: "architecture_lab" }
1 · COMMANDfind와 대상을 식별

architecture_lab.orders에서 Filter와 일치하는 Document를 찾는 요청으로 해석합니다.

2 · RULES이 요청을 실행해도 되는가?

Namespace·권한·Session을 확인합니다. 이번 요청은 읽기이므로 Document Validator 적용 대상이 아닙니다.

3 · PLANNER어떤 경로로 찾을까?

조건에 사용할 수 있는 Index 후보를 검토합니다. 적합한 Index가 없으면 Collection Scan 경로를 사용합니다.

4 · EXECUTION선택한 Plan을 실행

Index Key를 찾고 연결된 Record를 읽어 Filter를 확인한 뒤 결과 Document를 반환합니다.

가능한 경로와 이번에 선택된 경로는 어떻게 다를까?
