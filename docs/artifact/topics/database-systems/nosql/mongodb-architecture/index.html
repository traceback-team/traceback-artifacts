01 · WHY

왜 RDBMS 말고 다른 모델이 필요했을까?

NoSQL은 하나의 제품이나 하나의 구조가 아니라, 관계형 Table 이외의 데이터 모델을 주 인터페이스로 삼는 Database 계열을 묶어 부르는 말입니다.

일반 개념 · 특정 제품에 한정하지 않음

NoSQL

“SQL을 절대 쓰지 않는다”는 뜻이 아닙니다. Document, Key–Value, Wide-column, Graph처럼 문제에 맞는 논리 모델과 접근 경로를 우선하는 큰 분류입니다. Cassandra처럼 SQL과 닮은 CQL을 쓰는 NoSQL도 있습니다.

RDBMS의 기본 관점

관계를 정규화한 Table

order_itemsorder_id · sku · qty · price
addressescustomer_id · city · postal_code

강점: 명시적 Schema, Join, Constraint와 범용 Query. 중복을 줄이고 관계의 무결성을 중앙에서 관리하기 좋습니다.

이분법 주의: 현대 RDBMS도 JSON·분산 기능을 제공하고 MongoDB도 Schema validation, Index, Join 성격의 $lookup, ACID transaction을 제공합니다. 차이는 “기능의 유무”보다 기본 모델과 최적화의 중심입니다. NoSQL은 RDBMS의 상위 버전이 아니라 다른 trade-off입니다.

02 · KINDS

다른 DB 형태는 무엇을 첫 번째 질문으로 삼을까?

같은 주문 데이터라도 가장 자주 묻는 질문이 다르면 알맞은 논리 형태도 달라집니다. 제품명보다 “어떤 접근을 싸게 만들려는가”를 먼저 봅니다.

대표 분류 · 실제 제품은 여러 모델을 함께 지원할 수 있음
KEY–VALUE · Redis 예

Key로 값을 바로 찾기

"order:1001" → bytes / hash

질문: 정확한 Key의 값은?

목적: Cache, session, counter처럼 Key 기반 접근이 중심일 때. Redis는 단순 byte string 외에도 hash·set·stream 등 여러 자료형을 제공합니다.

DOCUMENT · MongoDB 예

중첩된 Aggregate 찾기

{ _id: 1001,
customerId: 7,
items: [ ... ],
total: 37000 }

목적: 함께 변하고 읽히는 구조를 한 Document로 다룰 때. Field·배열을 Query하고 Secondary Index를 둘 수 있습니다.

WIDE-COLUMN · Cassandra 예

Partition 안의 정렬된 Row 읽기

partition: customer_7
cluster: ordered_at ↓
columns: status,total,...

목적: 큰 분산 Cluster에서 미리 정한 Query pattern을 Partition key와 clustering order로 빠르게 처리할 때.

GRAPH · Neo4j 예

관계 Path를 순회하기

(Customer)-[:PLACED]→(Order)
(Order)-[:CONTAINS]→(Product)
(Customer)-[:KNOWS]→(Customer)

목적: 추천·사기 탐지·의존성처럼 “몇 단계로 연결되었나?”가 핵심일 때. Node·Relationship·Property가 1급 구조입니다.

선택 질문: 내 데이터가 무엇처럼 생겼나? 보다 내 애플리케이션이 어떤 질문을 반복해서 하는가?가 먼저입니다.

실험의 주문 Document를 Driver 7.9.0으로 직렬화한 앞부분입니다. 첫 4 byte의 little-endian 값 0x000000ed는 BSON 전체 길이 237을 뜻합니다.

정확한 표현: WiredTiger가 “아무것도 모른다”기보다 업무 의미를 모른다고 해야 합니다. WiredTiger는 Key·Value, B-tree, Page, Transaction timestamp와 압축을 알아야 하지만, 그 bytes가 주문의 customerId인지 배송지인지 판단하지 않습니다. Field 의미·Validator·Query semantics는 위의 MongoDB 계층 책임입니다.

05 · DURABILITY

Index·Transaction·WAL은 어느 층에 있을까?

셋 모두 MongoDB Server와 WiredTiger가 협력하는 기능입니다. 사용자가 선언하는 논리 기능과 저장 엔진이 수행하는 물리 메커니즘을 한쪽에만 놓지 않습니다.

공통 개념 + MongoDB/WiredTiger 구현
INDEX

전체를 읽지 않는 별도 탐색 구조

Query: customerId=7, status=PAID
Query Planner가 customer_status 선택
Index B-tree key → Record 위치 → Document

Index 정의와 Plan 선택은 mongod, Index의 Key·Page·파일 갱신은 WiredTiger가 담당합니다. 실험에서는 1 key와 1 document를 검사해 1건을 반환했습니다.

TRANSACTION

여러 변경을 한 단위로 Commit

Session + txnNumber: 3
Alice −15,000 · Bob +15,000
commitTransaction → 둘 다 공개

한 Document 쓰기는 원자적입니다. 여러 Document를 모두 적용하거나 모두 취소하려면 transaction을 사용합니다. 실험은 snapshot read concern과 w: majority, j: true로 commit했습니다.

WAL / JOURNAL

Data Page보다 먼저 복구 기록

Transaction의 data + index 변경
WiredTiger Journal record
Checkpoint 이후 오래된 Journal 정리

Write-ahead logging은 변경된 Page가 최종 위치에 반영되기 전에 복구 정보를 순차 Journal에 기록하는 원리입니다. Crash 후 마지막 checkpoint 이후 변경을 재생합니다.

WiredTiger Journal

한 mongod의 local crash recovery용 write-ahead log입니다. `/data/db/journal/WiredTigerLog...`로 관찰했습니다.

Replication Oplog

Replica set member끼리 data 변경을 복제하는 논리 operation log입니다. Journal과 목적·소비자가 다르며 둘을 같은 WAL 파일로 부르면 안 됩니다.

BSON

Binary JSON. JSON과 닮은 Document를 길이와 Type 정보가 포함된 binary 형식으로 표현합니다.

Wire protocol

Client Driver와 MongoDB Server가 network에서 message를 주고받는 byte 규칙입니다. 현대 요청은 주로 OP_MSG를 사용합니다.

Page

Storage engine이 B-tree를 탐색·cache·disk block으로 reconcile할 때 다루는 내부 단위입니다. “Document 하나 = Page 하나”가 아닙니다.

Checkpoint

특정 시점의 일관된 tree 상태를 disk에 남긴 복구 기준점입니다. Journal은 그 이후 변경을 보완합니다.

Cache

자주 쓰거나 변경 중인 Page를 memory에 둔 영역입니다. WiredTiger cache와 OS filesystem cache는 별도 층입니다.

Compression

CPU를 사용해 disk에 쓸 byte 양을 줄이는 과정입니다. MongoDB는 collection block과 index prefix에 서로 다른 기본 압축을 둡니다.
