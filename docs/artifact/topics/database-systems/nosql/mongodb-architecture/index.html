NoSQL 전체 구조

먼저 RDBMS와 무엇이 다른지, 어떤 문제 때문에 여러 NoSQL 모델이 생겼는지 봅니다. MongoDB의 깊은 내부는 다음 두 페이지에서 같은 주문 하나를 따라갑니다.

핵심: NoSQL은 RDBMS를 없애는 기술이 아니라, 반복되는 질문과 확장 방식에 맞춰 다른 논리 모델을 첫 번째 인터페이스로 선택한 Database 계열입니다.

APPLICATIONClient · 주문 객체와 Query

업무 의미와 읽기·쓰기 의도를 만듭니다.

LIBRARY / PROTOCOLMongoDB Driver · BSON / OP_MSG

언어 객체를 전송 가능한 bytes로 바꿉니다.

MONGOD PROCESSCommand / Query 처리

검증하고 실행 계획을 선택합니다.

STORAGE ENGINEWiredTiger · Record / Page / Journal

Key·Value와 파일 bytes를 저장·복구합니다.

01 · WHY

왜 관계형 Table 외의 모델이 필요했을까?

데이터가 “어떻게 생겼는가”보다 애플리케이션이 “어떻게 함께 읽고 쓰는가”를 우선하고 싶을 때 다른 모델이 유용합니다.

일반 개념 · 제품별 구현과 분리

NoSQL

“SQL을 절대 쓰지 않는다”는 뜻이 아닙니다. Document, Key–Value, Wide-column, Graph처럼 관계형 Table 이외의 논리 모델을 주 인터페이스로 삼는 큰 분류입니다. Cassandra처럼 SQL과 닮은 CQL을 사용하는 NoSQL도 있습니다.

RDBMS의 기본 관점

관계를 정규화한 Table

ordersid · customer_id · status · total
order_itemsorder_id · sku · qty · price
addressescustomer_id · city · postal_code

명시적 Schema, Constraint, Join과 범용 Query가 강점입니다.

↔
Document DB의 기본 관점

함께 읽는 Aggregate를 한 Document로

orders / _id: 1001customerId · address {…}
items [{…}] · status · total

중첩 구조와 Aggregate 단위 읽기·원자적 갱신이 강점입니다.

이분법 주의: 현대 RDBMS도 JSON·분산 기능을 제공하고 MongoDB도 Schema validation, Index, $lookup, ACID transaction을 제공합니다. 차이는 기능의 유무보다 기본 모델과 최적화의 중심입니다.

02 · KINDS

같은 주문을 어떤 모양으로 저장할 수 있을까?

대표 형태는 저장 모양뿐 아니라 가장 싸게 답하려는 질문이 다릅니다.

대표 분류 · 실제 제품은 여러 모델을 함께 지원 가능
KEY–VALUE · Redis 예

Key로 바로 찾기

"order:1001" → value

Cache·session·counter처럼 정확한 Key 접근이 중심일 때.

DOCUMENT · MongoDB 예

중첩 Aggregate 찾기

{ _id:1001,
items:[…], total:37000 }

함께 변하고 읽히는 Field·배열을 한 단위로 다룰 때.

WIDE-COLUMN · Cassandra 예

Partition 안에서 읽기

partition: customer_7
cluster: ordered_at ↓

큰 분산 Cluster에서 미리 정한 Query pattern을 처리할 때.

GRAPH · Neo4j 예

관계 Path 순회

(Customer)-[:PLACED]→(Order)
-[:CONTAINS]→(Product)

추천·사기 탐지처럼 연결과 경로 자체가 질문일 때.
