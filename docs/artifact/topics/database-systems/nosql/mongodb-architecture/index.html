PRESENTATION QUESTION

현대 RDBMS와 NoSQL의 경계는 무엇인가?

PostgreSQL도 JSONB와 Sharding을 쓰고, MongoDB도 JOIN과 Transaction을 지원합니다. MongoDB와 InnoDB는 모두 B-tree 계열 구조를 사용합니다. 그렇다면 경계는 어디에 남아 있을까요?

발표의 결론 후보: 경계는 기능의 유무보다 기본 논리 모델, 짧게 만드는 처리 경로, 일관성을 묶는 범위, 그 선택을 운영하는 비용에 있습니다. 이 결론을 같은 주문과 Docker 실험으로 검증합니다.

1 · LOGICAL INTERFACE애플리케이션이 보는 기본 데이터 단위
Table·RelationJSONB RowDocument
2 · DBMS RESPONSIBILITY요청을 실행하고 규칙을 지키는 방법
Planner·JOINTransactionSharding
3 · PHYSICAL STORAGE결국 bytes를 찾고 지속하는 공통 도구
B-tree·PageCacheWAL·Journal

아래로 갈수록 기술은 비슷해질 수 있지만, 위에서 제공하는 기본 계약은 달라질 수 있습니다.

01 · WHY

어떤 비용이 NoSQL이라는 선택을 만들었을까?

NoSQL은 “RDBMS에 기능이 없어서” 등장한 단일 기술이 아닙니다. 2000년대 대규모 서비스가 반복해서 마주친 비용과, 그 비용을 줄이기 위해 포기하거나 옮긴 책임을 순서대로 봅니다.

출발점 · RDBMS

사실을 나누고 관계를 Database가 지킨다

정규화, Constraint, JOIN, Transaction은 중복을 줄이고 다양한 질문과 정확한 변경을 가능하게 했습니다.

→
2000년대 · 운영 압력

한 서버 밖에서 조합·조정 비용이 커졌다

사용자와 데이터가 급증하자 여러 서버를 오가는 읽기, 쓰기 조정, 가변 데이터 배포가 자주 쓰는 경로의 병목이 됐습니다.

→
NoSQL 계열 · 설계 전환

접근 경로와 분산 경계를 먼저 정한다

Key·Document·Partition·Graph 경로에 맞춰 데이터를 배치해, 범용 조합 일부를 줄이고 주된 요청을 예측 가능하게 만들었습니다.

여기까지가 역사적 배경입니다. MongoDB의 BSON Document·Embedding·Shard Key는 이 문제의식에 대한 한 제품의 답이며, 모든 NoSQL의 공통 정의가 아닙니다.

1

관련 데이터를 매 요청마다 다시 조립한다

예: 주문, 배송지, 주문 항목을 정규화한 Table에서 한 주문 화면을 만든다.

문제 발생JOIN 입력이 커지거나 반복된다

JOIN은 분리된 관계를 Query 시점에 다시 결합하는 연산입니다.

→
내부 동작과 비용찾고 · 비교하고 · 보관하고 · 읽는다
Index 탐색 반복CPU 비교·HashHash·Sort MemoryCache miss 시 Random I/O
→
설계 전략RDBMS도 미리 합칠 수 있다

비정규화·Materialized View·JSONB로 조립을 줄입니다. MongoDB는 함께 읽는 값을 Document에 Embed하는 방식을 기본 모델로 삼기 쉽습니다.

→
이점 ↔ 제약한 번의 읽기 ↔ 중복 관리

Embedding은 Database 연산과 Random I/O를 줄일 수 있지만, 중복 갱신·Document 성장·횡단 질의 비용을 만듭니다.

2

서비스마다 Field가 다른데 한 Schema를 배포한다

예: 상품 종류마다 속성이 다르고, 구버전·신버전 데이터가 함께 존재한다.

문제 발생형태 변화가 배포 일정과 결합된다

관계형 Column 변경은 DDL(Data Definition Language)로 Schema를 바꿉니다.

→
내부 동작과 비용DDL·Lock·검증 범위를 판단한다

ALTER 종류와 DB Version에 따라 Catalog만 바꾸거나 Table을 다시 쓰며, Lock 충돌이 생길 수 있습니다. Constraint는 쓰기 시 형태를 검증합니다.

→
설계 전략NULL·별도 Table·JSONB도 가능하다

RDBMS 안에서 가변 부분만 JSONB로 둘 수 있습니다. MongoDB는 Field 추가 DDL 없이 Document별 형태를 달리하고 선택적 Validator를 둡니다.

→
이점 ↔ 제약배포 독립성 ↔ 검증 책임 이동

유연한 저장은 버전 전환을 점진화하지만, 호환성·기본값·과거 Document Migration을 애플리케이션과 운영이 책임집니다.

3

데이터를 여러 서버에 나누면 관계도 흩어진다

예: 주문과 고객이 서로 다른 Shard에 있어 한 요청·Transaction이 여러 Node를 건넌다.

문제 발생단일 서버의 CPU·Memory·I/O 한계

Sharding은 데이터를 Key 범위로 나누어 여러 서버가 처리하게 하는 수평 확장 방식입니다.

→
내부 동작과 비용분산 JOIN·Transaction은 통신과 조정이 필요하다
Network I/O·왕복결과 MergeCommit 조정·Log일관성·Retry
→
설계 전략양쪽 모두 Sharding할 수 있다

RDBMS도 분산 제품·Application Sharding을 쓸 수 있습니다. MongoDB는 Shard Key와 Embedding으로 주된 요청이 한 Shard·Document에 머물도록 설계합니다.

→
이점 ↔ 제약짧은 지역 경로 ↔ 사전 결정

잘 맞는 Key는 확장을 단순화하지만, 나쁜 Key는 Hotspot·Scatter–Gather를 만들고 Cross-shard JOIN·Transaction은 다시 비싸집니다.

역사와 MongoDB 특징, NoSQL 계열 용어 구분
역사적 등장 배경Bigtable·Dynamo가 대표한 대규모 분산, 장애 허용, 예측 가능한 Key·Partition 경로의 문제의식
MongoDB의 설계 특징BSON Document, Embedded data, $lookup, 다중 Document Transaction, Sharded Cluster라는 구체적 선택
Key–Value

정확한 Key로 값을 찾는 경로를 우선합니다.

Document

중첩 Field·배열을 Aggregate로 다룹니다.

Wide-column

Partition과 정해진 Query pattern을 중심으로 배치합니다.

Graph

Node 사이 관계와 Path 탐색을 중심에 둡니다.

Embedding은 함께 읽을 데이터를 한 Document에 두는 논리 모델링이고, Sharding은 Shard Key로 데이터를 여러 서버에 나누는 물리 배치입니다. 둘은 서로 대체하지 않습니다.

판단 기준: RDBMS로도 해결 가능한가를 먼저 묻고, 반복되는 주 경로의 비용이 별도 논리 모델과 운영 책임을 감수할 만큼 큰지 확인한다.

02 · OVERLAP

기능의 경계가 겹치면 무엇이 달라질까?

“된다/안 된다”를 비교하지 않습니다. 같은 기능을 사용할 때 기본 경로가 얼마나 짧은지, 어떤 규칙과 운영 책임이 추가되는지를 비교합니다.

일반 원리 · 제품 Version과 배치에 따라 실제 비용은 달라짐
의문 1

RDBMS도 JSONB와 Sharding을 지원하는데 왜 NoSQL이 필요한가?

가능 여부가 아니라 주된 데이터 경계와 분산 배치가 제품의 기본값인지 묻습니다.

PostgreSQL JSONB·분산 확장

Table·Row·SQL Transaction을 유지하면서 일부 Field를 Document처럼 저장하거나 Shard를 추가합니다.

↔
MongoDB Document·Sharded Cluster

Document와 Shard Key를 주 인터페이스로 삼지만 중복, Shard Key 변경, Scatter–Gather를 관리합니다.

경계: RDBMS 안에 Document를 넣을지, Document를 전체 Schema와 분산의 기본 단위로 삼을지.

의문 2

MongoDB도 JOIN과 Transaction을 지원하는데 RDBMS와 무엇이 다른가?

$lookup과 다중 Document Transaction이 있어도 한 Document 변경과 같은 비용은 아닙니다.

한 Row·Table 관계가 기본

RDBMS는 Foreign Key·Constraint·JOIN·여러 Row Transaction을 모델의 중심에 둡니다.

↔
한 Document Aggregate가 기본

MongoDB는 함께 읽고 쓰는 값을 Embed해 단일 Document 경로를 짧게 하고, 분리했을 때 $lookup·Transaction 비용을 냅니다.

경계: 기능 이름이 아니라 가장 자주 쓰는 연산이 한 저장 단위 안에서 끝나는가.

의문 3

MongoDB와 InnoDB가 B-tree를 쓰는데 왜 다른 DBMS인가?

B-tree는 물리적으로 Key를 찾는 도구이며, 애플리케이션이 보는 논리 계약 자체는 아닙니다.

공통 물리 도구

B-tree, Page, Cache, WAL 계열 복구 기록은 여러 DBMS가 공유합니다.

≠
서로 다른 상위 계약

SQL Table·Constraint·JOIN과 BSON Document·Embedding·Shard routing은 Parser부터 모델링 방식까지 다릅니다.

경계: 같은 자료구조를 쓴다는 사실만으로 같은 DBMS 계열이 되지는 않습니다.

검증 방법: 같은 주문을 세 가지 논리 모델로 저장하고, 같은 질문의 실행 경로를 비교한다.

03 · ONE ORDER

같은 주문을 세 모델은 어떻게 표현할까?

주문 _id: 1001, 배송지 하나, 항목 다섯 개를 같은 의미로 유지합니다. 모양이 바뀌면 읽기와 수정의 작업 단위가 달라집니다.

POSTGRESQL · NORMALIZED

관계를 세 Table로 분리

orders_normid · customer_id · status · total
order_shipping_normorder_id · city · postal_code
order_items_normorder_id · line_no · sku · quantity
3 Index Scan→ JOIN·Aggregate →주문 JSON

항목 하나는 작은 Row로 바꿀 수 있고 관계별 Index를 만들기 쉽지만, 전체 주문 응답은 다시 조립해야 합니다.

POSTGRESQL · JSONB

Row 안에 Binary JSON Aggregate

orders_jsonbid bigint PRIMARY KEY
doc jsonb
doc{ customerId, status,
shippingAddress, items[], total }
PK Index Scan→ 1 Row →주문 JSONB

SQL Transaction과 Table 경계를 유지하면서 한 Aggregate를 읽지만, 배열 검색·부분 수정에 JSON 경로와 GIN 설계가 필요합니다.

MONGODB · EMBEDDED

Collection의 기본 단위가 Document

orders / _id: 1001{ customerId, status,
shippingAddress:{…},
items:[…], total }
Compound·Multikey Index{customerId,status}
{items.sku}
_id Index→ RecordId →BSON Document

Document 경계와 Driver 객체가 가깝지만, 중복 Field·Document 성장·다중 Document 규칙은 별도로 설계합니다.

JSONB와 MongoDB Document는 겉모양이 비슷해도 위치가 다릅니다. JSONB는 PostgreSQL Row의 한 타입이고, MongoDB Document는 Collection·Index·원자적 변경·Shard 배치의 기본 단위입니다.

04 · PHYSICAL

아래로 내려가면 왜 다시 비슷해질까?

세 엔진 모두 Key를 정렬하고 Page를 Cache하며 복구 기록을 남깁니다. 하지만 Index가 실제 Row·Document까지 이어지는 참조 방식은 다릅니다.

POSTGRESQL HEAP

Index와 Table Heap 분리

B-tree Index
key → TID
Heap Page
Tuple 읽기

TID는 Heap Tuple의 Page·slot 위치입니다. JSONB도 결국 Heap Tuple의 Column 값입니다.

MYSQL · INNODB

Primary Key clustered B-tree

Secondary B-tree
key → Primary Key
Clustered B-tree leaf
Row 데이터

Primary Key B-tree의 leaf가 Row를 담습니다. Secondary Index는 Primary Key를 통해 다시 찾습니다.

MONGODB · WIREDTIGER

Index와 Record Store B-tree

Index B-tree
key → RecordId
Record Store B-tree
RecordId → BSON

일반 Collection 기준입니다. Clustered Collection은 _id가 Record Store key인 예외입니다.

B-tree는 분류 기준이 아니라 구현 재료입니다. DBMS 분류는 위 계층에서 어떤 논리 객체를 주 인터페이스로 삼고, 어떤 관계·원자성·분산 경로를 기본 책임으로 두는지까지 봐야 합니다.

Record·Page·Block과 WiredTiger Clustered Collection 더 보기

Record는 한 데이터의 저장 단위, Page는 엔진이 여러 Record·Index entry를 묶어 관리하는 단위, Block은 파일·장치 계층의 공간 또는 I/O 단위입니다.

06 · DECISION

어떤 상황에서 어떤 선택이 합리적일까?

실험의 가장 빠른 숫자 하나가 Schema를 결정하지 않습니다. 실제 주된 접근 경로, 지켜야 할 관계, 분산 범위와 운영 능력을 함께 봅니다.

POSTGRESQL · NORMALIZED

관계와 다양한 질문이 중심

합리적 조건: 여러 업무가 같은 사실을 공유하고, 관계 Constraint·다양한 JOIN·횡단 집계가 중요합니다.

POSTGRESQL · JSONB

RDBMS 계약 안의 일부 Aggregate

합리적 조건: Transaction·SQL은 유지하면서 일부 가변 구조를 한 Row로 읽고, JSON 경로 Index를 관리할 수 있습니다.

MONGODB · DOCUMENT

Document가 애플리케이션의 기본 경계

합리적 조건: 함께 읽고 쓰는 Aggregate가 명확하고 그 Document·Shard 경로를 독립적으로 확장할 가치가 있습니다.

1 · RDBMS로 시작 가능한가?

관계·Transaction·임의 Query가 중심인 초기 서비스라면 단순한 출발점입니다.

→
2 · 반복 비용을 측정했는가?

Index·JSONB·Cache·Read replica·Partition으로 목표를 만족하는지 확인합니다.

→
3 · 별도 DB 책임이 분명한가?

원본 소유자, 허용 지연, 재시도·재구축과 운영 책임을 정한 뒤 추가합니다.

NoSQL이 불필요할 수 있습니다. 현재 RDBMS가 목표 지연과 처리량을 만족하고 핵심 요구가 Transaction·Constraint·다양한 Join이며, 팀이 여러 DB의 Backup·Upgrade·장애 대응을 감당할 이유가 없다면 하나의 RDBMS가 더 안전합니다.

Polyglot Persistence는 언제 다음 단계가 되는가?
RDBMS · 원본주문·결제·재고를 Transaction으로 확정
Document·Key–ValueCatalog Aggregate·Session처럼 명확한 요청 경로 분리
파생 StoreCommit Event로 Timeline·Graph를 만들고 실패 시 재구축

여러 DB를 하나의 분산 Transaction으로 묶는 것이 아니라, 원본 Commit과 늦게 갱신될 수 있는 파생 데이터를 구분해야 합니다.

최종 결론: “어느 DB가 더 많은 기능을 가졌는가?”가 아니라 “어떤 경로를 기본값으로 짧게 만들고, 그 대가를 어디서 지불할 것인가?”를 선택한다.
