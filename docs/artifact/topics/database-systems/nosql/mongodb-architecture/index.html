아직 장단점을 판단하지 않고, _id: 1001 주문의 데이터가 어디에 놓이고 읽을 때 무엇을 거치는지만 관찰합니다.

Aggregate는 함께 다루는 업무 데이터 묶음입니다. 주문 Field·항목 배열·주소가 한 Document 안에 중첩되어 반환됩니다.

여기서는 모양만 기억합니다. RDBMS는 관계를 분리해 두고 읽을 때 조합하며, MongoDB는 주문 묶음을 Document 경계 안에 둡니다. 어느 방식이 유리한지는 03에서 요청 횟수와 서버 배치를 본 뒤 판단합니다.

03 · WHY & TRADE-OFF

구조를 봤으니, 이제 왜 이런 선택을 하는지 고민한다

RDBMS와 NoSQL 모두 여러 기능을 지원할 수 있습니다. 여기서는 기능 목록보다 주문 요청 한 번이 몇 개 데이터·서버를 거치는지와 그 대가를 비교합니다.

일반 개념 · 제품과 Version에 따라 세부 비용은 달라짐

출발점 · RDBMS

Table, 관계, Constraint(허용할 데이터 규칙), Transaction(여러 변경을 한 단위로 처리)을 Database가 관리합니다. 여러 Table을 Join(공통 값으로 결합)하고 관계를 정확히 지키는 범용성이 큰 강점입니다. 이 강점은 지금도 유효하며 NoSQL이 RDBMS를 대체하지 않았습니다.

주문 조회주문·상품·배송지를 매번 함께 읽는다요청마다 같은 Table 결합이 반복됨
상품 등록의류는 치수, 가전은 전압이 필요하다카테고리마다 선택 속성이 크게 다름
트래픽 분산고객 ID별 주문을 여러 서버에 나눈다관련 데이터가 다른 서버에 있으면 통신이 필요함
→
RDBMS로도 해결 가능반복되는 핵심 경로의 비용을 묻는다

Table 결합·중첩 데이터·Sharding(데이터를 Key 기준 여러 서버로 분할)이 가능해도, 요청마다 몇 개 서버와 데이터를 조정하는지가 지연과 장애 지점을 만듭니다.

→
NOSQL의 설계 목적자주 함께 쓰는 데이터를 먼저 배치

범용 조합 일부를 포기하고 주요 읽기·쓰기와 분산 경로를 짧게 만드는 선택입니다.

그래서 나온 선택: 2000년대의 대규모 인터넷 서비스는 수천 대 서버로 확장되는 저장과, 일부 서버가 고장 나도 서비스를 계속하는 높은 가용성을 요구했습니다. Google Bigtable과 Amazon Dynamo는 각각 대규모 분산 데이터와 식별자(Key)로 값을 찾는 저장을 위한 설계를 보여주었습니다. 이후 NoSQL은 관계형 Table 이외의 데이터 모델을 중심에 둔 여러 Database 계열을 묶어 부르는 이름이 되었습니다.

DOCUMENT 모델이 유리한 주문 상세

한 ID로 같은 묶음을 매우 자주 읽는다

  • 주문 당시 상품명·가격·배송지를 주문 안에 함께 보관한다.
  • 한 Document 읽기로 화면을 만들고 단일 Document로 갱신한다.
  • 대신 중복 데이터와 커지는 Document를 관리해야 한다.
관계형 모델이 유리한 상품·재고

하나의 사실을 여러 업무가 공유한다

  • 현재 상품·재고를 한 곳에서 갱신하고 여러 주문이 참조한다.
  • 다양한 조건으로 결합·집계하고 관계 규칙을 Database가 검사한다.
  • 대신 자주 쓰는 화면은 Join·Cache·별도 조회 모델로 최적화할 수 있다.

Sharding과 Embedding은 무엇이 다른가?

Embedding은 함께 쓸 데이터를 한 Record·Document 안에 두는 모델링이고, Sharding은 전체 데이터를 Key 기준으로 여러 서버에 나누는 배치입니다. 서로 대체하는 기능이 아닙니다.

EMBEDDING · 데이터 경계

주문 1001 안에 주문 항목·배송지를 함께 둔다

order:1001items […] · shippingAddress {…} · paidAt

관련 데이터가 한 Document에 있고 조회 조건에 Shard Key도 포함되면 한 번의 대상 조회로 반환할 수 있습니다. 하지만 자주 바뀌는 현재 재고까지 복제하면 여러 Document를 다시 고쳐야 합니다.

SHARDING · 서버 배치

customerId를 보고 담당 서버를 고른다

customerId: 7
Shard Key 포함
→
Shard A
고객 7
Shard B
고객 8
Shard C
고객 9
Shard Key 없는 status=PAID 조회: A·B·C에 보내고 결과를 합치는 Scatter–Gather가 될 수 있음

RDBMS도 분산 제품·Extension(확장 모듈)·애플리케이션 방식으로 Sharding할 수 있습니다. 같은 Shard Key로 관련 Table을 함께 배치하면 Join도 한 서버 안에서 끝납니다.

서버 간 통신 비용: 다른 서버의 데이터를 읽으면 요청 직렬화·Network 왕복·결과 병합·실패 재시도가 추가됩니다. MongoDB라도 Shard Key가 없거나 여러 Shard를 갱신하면 이 비용을 내며, RDBMS라도 관련 Row가 같은 Shard에 있으면 로컬 Join으로 끝낼 수 있습니다.

JOIN·Transaction·Sharding은 어느 쪽만 가능한 기능일까?

세 기능 모두 양쪽에서 가능할 수 있습니다. 중요한 것은 실행 범위가 한 Record(한 저장 단위)·한 서버인지, 여러 서버의 조정이 필요한지입니다.

JOIN / LOOKUP

분리된 데이터를 읽을 때 결합

RDBMS · SQL JOINMongoDB · Reference + $lookup

지원 여부보다 Index, 입력 건수, 같은 서버 배치 여부가 비용을 결정합니다.

TRANSACTION

여러 변경을 모두 적용하거나 취소

RDBMS · 여러 Row/TableMongoDB · 여러 Document/Shard

한 Row·Document보다 여러 Shard Transaction에 더 많은 잠금·합의·복구 조정이 필요합니다.

SHARDING

데이터와 부하를 여러 서버로 분산

RDBMS · 분산 제품/확장 모듈/직접 구성MongoDB · Sharded Cluster

좋은 Shard Key는 대상 서버를 좁히고, 나쁜 Key는 Broadcast나 한 Shard로 부하가 몰리는 Hotspot을 만듭니다.

상품마다 Field가 다르면 MongoDB만 답일까?

아닙니다. RDBMS에서도 문제의 범위에 따라 일반 Column, NULL(값 없음), JSONB(PostgreSQL의 Binary JSON 타입)를 선택할 수 있습니다.

RDBMS · NULLABLE COLUMN

소수의 안정적인 선택 Field

예: 주문의 gift_message. PostgreSQL은 Column을 추가하고 기존 Row는 NULL로 둘 수 있으며 Row 전체 재작성도 피할 수 있습니다. 타입·Constraint·SQL 분석이 쉽지만 DDL(Table 구조 변경) Lock과 배포 조정은 필요하고, 선택 Field가 수백 개면 희소한 Table이 됩니다.

RDBMS · JSONB

카테고리별로 다른 상품 속성

예: attributes.voltage 또는 attributes.size. PostgreSQL JSONB는 JSON 내부 값을 찾는 GIN Index를 만들 수 있습니다. 관계형 핵심은 유지하지만 경로별 타입·규칙·Index를 별도로 설계해야 합니다.

MONGODB · DOCUMENT

가변 중첩 구조가 업무의 기본 단위

예: 상품 API가 속성·배열 전체를 Document로 읽고 갱신. 표현 변환이 줄지만 Schema가 사라지는 것은 아니며 구조 검증·Index·이전 Document 변환을 관리해야 합니다.

결론: “Column 추가가 어려워서 MongoDB”는 충분한 이유가 아닙니다. Column·NULL·JSONB로 해결 가능한지 먼저 보고, 애플리케이션의 주된 읽기·쓰기 경계 자체가 Document일 때 MongoDB의 기본 모델이 주는 단순성이 비용을 이기는지 판단합니다.

2006–2007의 문제 설정

분산을 제품의 출발점으로 삼았다
