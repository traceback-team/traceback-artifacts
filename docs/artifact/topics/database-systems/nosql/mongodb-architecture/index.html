PRESENTATION QUESTION

현대 RDBMS와 NoSQL의 경계는 무엇인가?

PostgreSQL도 JSONB와 Sharding을 쓰고, MongoDB도 JOIN과 Transaction을 지원합니다. MongoDB와 InnoDB는 모두 B-tree 계열 구조를 사용합니다. 그렇다면 경계는 어디에 남아 있을까요?

발표의 결론 후보: 경계는 기능의 유무보다 기본 논리 모델, 짧게 만드는 처리 경로, 일관성을 묶는 범위, 그 선택을 운영하는 비용에 있습니다. 이 결론을 같은 주문과 Docker 실험으로 검증합니다.

1 · LOGICAL INTERFACE애플리케이션이 보는 기본 데이터 단위
Table·RelationJSONB RowDocument
2 · DBMS RESPONSIBILITY요청을 실행하고 규칙을 지키는 방법
Planner·JOINTransactionSharding
3 · PHYSICAL STORAGE결국 bytes를 찾고 지속하는 공통 도구
B-tree·PageCacheWAL·Journal

아래로 갈수록 기술은 비슷해질 수 있지만, 위에서 제공하는 기본 계약은 달라질 수 있습니다.

01 · BACKGROUND

NoSQL은 왜 등장했을까?

기능 목록을 비교하기 전에, 대규모 서비스가 어떤 운영 비용을 마주했고 설계의 초점을 어디로 옮겼는지부터 봅니다.

핵심 답: NoSQL은 RDBMS가 무능해서가 아니라, 다양한 질문을 다루는 범용성 일부보다 특정 접근 경로·수평 확장·장애 허용을 먼저 최적화할 필요가 커지면서 등장한 데이터 모델 계열입니다.

출발점 · RDBMS

사실을 나누고 관계를 DBMS가 지킨다

정규화, 제약 조건, JOIN, 트랜잭션으로 중복을 줄이고 다양한 질문과 정확한 변경을 지원합니다.

→
2000년대 · 운영 압력

한 서버 밖의 조합·조정 비용이 커진다

사용자와 데이터가 급증하자 서버 간 읽기, 쓰기 조정, 장애 복구가 자주 쓰는 경로의 병목이 됐습니다.

→
NoSQL 계열 · 목적별 설계

범용 관계 모델 하나보다 자주 쓰는 요청을 우선한다

서비스 규모와 데이터 형태가 다양해지자, 키 조회·문서 묶음·대규모 분산·관계 탐색처럼 특정 요청에 특화된 데이터베이스가 등장했습니다.

역사적 배경과 MongoDB는 구분해야 합니다. MongoDB의 BSON 문서·Embedding·Shard Key는 이 문제의식에 대한 한 제품의 답이지, 모든 NoSQL의 공통 정의가 아닙니다.

1

관련 데이터를 매 요청마다 다시 조립한다

예: 주문, 배송지, 주문 항목을 정규화한 Table에서 한 주문 화면을 만든다.

문제 발생JOIN 입력이 커지거나 반복된다

JOIN은 분리된 관계를 Query 시점에 다시 결합하는 연산입니다.

→

비정규화·Materialized View·JSONB로 조립을 줄입니다. MongoDB는 함께 읽는 값을 Document에 Embed하는 방식을 기본 모델로 삼기 쉽습니다.

→

Embedding은 Database 연산과 Random I/O를 줄일 수 있지만, 중복 갱신·Document 성장·횡단 질의 비용을 만듭니다.

2

가변 필드를 관계형 스키마에 계속 추가해야 한다

예: 상품 유형마다 속성이 다르고, 구버전·신버전 데이터가 함께 존재한다.

문제 발생 · PostgreSQL컬럼 변화가 DDL 배포와 연결된다

고정 컬럼에 속성을 넣으려면 DDL(데이터 정의어)로 스키마를 바꾸고 애플리케이션 배포 순서를 맞춥니다.

→
내부 동작과 비용 · PostgreSQLDDL·잠금·검증 범위가 작업마다 다르다

변경 종류와 버전에 따라 카탈로그만 바꾸거나 테이블을 스캔·재작성합니다. 잠금은 동시 질의와 충돌할 수 있고, 제약 조건은 기존·신규 데이터를 검증합니다.

→
설계 전략 · PostgreSQL ↔ MongoDB두 DB 모두 유연한 형태를 선택할 수 있다

PostgreSQL은 NULL 허용 컬럼·별도 테이블·JSONB로 가변 부분을 분리합니다. MongoDB는 필드 추가 DDL 없이 문서별 형태를 달리하고 선택적 Validator를 둡니다.

→
실제 비용 · 선택별 Trade-off유연성은 무료가 아니라 책임의 위치를 바꾸다

PostgreSQL 컬럼은 제약을 중앙에서 지키지만 DDL·잠금 비용을 냅니다. JSONB는 경로 인덱스·검증을, MongoDB는 문서 버전·기본값·Validator·인덱스·과거 데이터 이관을 설계해야 합니다.

3

여러 서버로 나누려면 누가 라우팅과 재분배를 맡을까?

예: 주문이 늘어 단일 DB 서버의 저장 용량·처리량 한계를 넘어선다.

문제 발생 · 다중 서버 샤딩실제 수평 확장은 여러 서버가 필요하다

단일 서버 파티셔닝은 한 DB 인스턴스 안에서 나누고, 샤딩은 여러 서버가 데이터의 일부를 각각 맡습니다. MongoDB도 수평 확장하려면 여러 샤드 서버가 필요합니다.

→
제품 경계 · PostgreSQL ↔ MongoDB가능 여부가 아니라 통합 범위가 다르다

기본 PostgreSQL은 여러 서버의 샤딩·라우팅·재분배를 통합 제공하지 않아 별도 솔루션이나 애플리케이션 구현이 필요합니다. MongoDB는 이 기능을 샤딩 클러스터에 통합합니다.

→
제품 이점 · MongoDB라우팅과 재분배를 DBMS가 함께 제공한다

Shard Key가 데이터 배치를 정하고, mongos가 요청을 대상 샤드로 라우팅하며, Balancer가 샤드 간 데이터 범위를 재분배합니다. 커스텀 분산 구성 일부를 줄일 수 있는 것이 선택 이유가 됩니다.

02 · DATA MODELS

NoSQL은 하나의 데이터 모델일까?

같은 NoSQL이라도 애플리케이션에 보이는 단위와 잘 답하는 질문이 다릅니다.

핵심 답: NoSQL은 키–값, 문서, 와이드 컬럼, 그래프처럼 서로 다른 접근 경로를 기본값으로 삼는 계열입니다. MongoDB는 그중 문서 모델의 예시입니다.

모델 · 대표 DB기본 형태잘 답하는 질문대가
키–값Redissession:42 → {...}이 키의 값은 무엇인가?관계·범위 질의는 제한적
문서MongoDB{ order, items[] }함께 읽고 쓰는 주문 묶음은?중복·문서 성장·횡단 규칙 관리
와이드 컬럼Apache Cassandra파티션 키 + 정렬 컬럼이 파티션의 시간·범위 데이터는?질의 패턴을 먼저 정해야 함
그래프Neo4j(고객)-[구매]->(상품)어떤 관계 경로로 연결되는가?탐색 전문성과 별도 운영 비용

혼동하지 않기: 내장(Embedding)은 함께 읽을 데이터를 한 문서에 두는 논리 모델링이고, 샤딩(Sharding)은 샤드 키로 데이터를 여러 서버에 나누는 물리 배치입니다.

03 · SAME ORDER

같은 주문을 세 모델은 어떻게 표현할까?

주문 _id: 1001, 배송지 하나, 항목 다섯 개를 같은 의미로 유지하며 모양만 바꿔 봅니다.

핵심 답: 데이터의 모양은 단순한 표현 차이가 아니라 한 번에 읽고 쓰며 원자적으로 바꾸는 작업 단위를 결정합니다.

POSTGRESQL · 정규화

관계를 세 테이블로 분리

orders_normid · customer_id · status · total
order_shipping_normorder_id · city · postal_code
order_items_normorder_id · line_no · sku · quantity
인덱스 탐색 3회→ JOIN·집계 →주문 JSON

항목 하나는 작은 행으로 바꿀 수 있고 관계별 인덱스를 만들기 쉽지만, 전체 주문 응답은 다시 조립해야 합니다.

POSTGRESQL · JSONB

행 안에 이진 JSON 주문 묶음

orders_jsonbid bigint PRIMARY KEY
doc jsonb
doc{ customerId, status,
shippingAddress, items[], total }
PK 인덱스 탐색→ 1개 행 →주문 JSONB

SQL 트랜잭션과 테이블 경계를 유지하면서 한 주문 묶음을 읽지만, 배열 검색·부분 수정에 JSON 경로와 GIN 설계가 필요합니다.

MONGODB · 내장 문서

컬렉션의 기본 단위가 문서

orders / _id: 1001{ customerId, status,
shippingAddress:{…},
items:[…], total }
복합·멀티키 인덱스{customerId,status}
{items.sku}
_id 인덱스→ 1개 문서 →주문 묶음

문서 경계와 드라이버 객체가 가깝지만, 중복 필드·문서 성장·다중 문서 규칙은 별도로 설계합니다.

JSONB와 MongoDB 문서는 겉모양이 비슷해도 위치가 다릅니다. JSONB는 PostgreSQL 행의 한 타입이고, MongoDB 문서는 컬렉션·인덱스·원자적 변경·샤드 배치의 기본 단위입니다.

04 · COSTS

데이터 모델이 비용을 어디로 옮길까?

앞에서 본 같은 주문을 기준으로 JOIN, 스키마 변경, 샤딩의 실제 작업을 비교합니다.

핵심 답: 정규화는 읽기 시점의 조립 비용을 내고, 주문 묶음으로 저장하면 중복·부분 수정·횡단 규칙의 비용을 냅니다. 샤딩으로 서버가 나뉘면 서버 간 통신과 합의가 추가됩니다.

판단 기준: RDBMS로도 비정규화·JSONB·샤딩을 적용할 수 있습니다. 별도 NoSQL을 선택할 때는 그 경로를 제품의 기본값으로 삼을 이익이 운영 복잡도보다 큰지 봅니다.

단위는 ms입니다. Cold Cache, 동시 사용자 증가, Sharding·Failover, 장시간 Update 뒤 Vacuum·Compaction은 측정하지 않았습니다. InnoDB는 물리 구조 비교에만 사용했으며 이 성능 실험 대상이 아닙니다.

관찰된 Trade-off: 주문을 한 묶음으로 저장하면 한 주문 응답은 바로 읽기 쉽고, 항목을 별도 관계로 분리하면 여러 주문을 가로지르는 SKU 질문은 인덱스만으로 답하기 쉽습니다.

06 · DECISION

어떤 상황에서 어떤 선택이 합리적일까?

실험의 가장 빠른 숫자 하나가 Schema를 결정하지 않습니다. 실제 주된 접근 경로, 지켜야 할 관계, 분산 범위와 운영 능력을 함께 봅니다.

POSTGRESQL · NORMALIZED

관계와 다양한 질문이 중심

합리적 조건: 여러 업무가 같은 사실을 공유하고, 관계 Constraint·다양한 JOIN·횡단 집계가 중요합니다.

POSTGRESQL · JSONB

RDBMS 계약 안의 일부 Aggregate

합리적 조건: Transaction·SQL은 유지하면서 일부 가변 구조를 한 Row로 읽고, JSON 경로 Index를 관리할 수 있습니다.

MONGODB · DOCUMENT

Document가 애플리케이션의 기본 경계

합리적 조건: 함께 읽고 쓰는 Aggregate가 명확하고 그 Document·Shard 경로를 독립적으로 확장할 가치가 있습니다.

1 · RDBMS로 시작 가능한가?

관계·Transaction·임의 Query가 중심인 초기 서비스라면 단순한 출발점입니다.

2 · 반복 비용을 측정했는가?

Index·JSONB·Cache·Read replica·Partition으로 목표를 만족하는지 확인합니다.

→
3 · 별도 DB 책임이 분명한가?

원본 소유자, 허용 지연, 재시도·재구축과 운영 책임을 정한 뒤 추가합니다.

NoSQL이 불필요할 수 있습니다. 현재 RDBMS가 목표 지연과 처리량을 만족하고 핵심 요구가 Transaction·Constraint·다양한 Join이며, 팀이 여러 DB의 Backup·Upgrade·장애 대응을 감당할 이유가 없다면 하나의 RDBMS가 더 안전합니다.

Polyglot Persistence는 언제 다음 단계가 되는가?
RDBMS · 원본주문·결제·재고를 Transaction으로 확정
Document·Key–ValueCatalog Aggregate·Session처럼 명확한 요청 경로 분리
파생 StoreCommit Event로 Timeline·Graph를 만들고 실패 시 재구축

여러 DB를 하나의 분산 Transaction으로 묶는 것이 아니라, 원본 Commit과 늦게 갱신될 수 있는 파생 데이터를 구분해야 합니다.

최종 결론: “어느 DB가 더 많은 기능을 가졌는가?”가 아니라 “어떤 경로를 기본값으로 짧게 만들고, 그 대가를 어디서 지불할 것인가?”를 선택한다.
