01 · WHY

왜 NoSQL이 등장했고, 언제 쓰는가?

웹 서비스의 데이터와 트래픽이 여러 서버로 커지고, 데이터 모양과 주된 조회 방식이 다양해지면서 모든 문제를 관계형 Table 하나의 관점으로 푸는 비용이 커졌습니다.

일반 개념 · 특정 제품의 저장 엔진과 분리

NoSQL

“SQL을 절대 쓰지 않는다”는 뜻이 아닙니다. Document, Key–Value, Wide-column, Graph처럼 관계형 Table 이외의 논리 모델을 주 인터페이스로 삼는 큰 분류입니다. Cassandra처럼 SQL과 닮은 CQL을 사용하는 NoSQL도 있습니다.

규모데이터·트래픽이 여러 서버로 증가한 장비를 키우는 것만으로 감당하기 어려워짐
모양중첩 객체와 자주 달라지는 Field분리된 Table과 Schema 변경 비용이 커질 수 있음
질문Key·Aggregate·경로처럼 반복되는 접근범용 Join보다 특정 조회가 훨씬 중요해짐
→
RDBMS가 불가능해서가 아님관계형 모델의 범용성에 드는 비용

Join·Schema migration·애플리케이션 Sharding 설계가 핵심 요구에 비해 복잡해질 수 있습니다.

→
NOSQL의 선택주된 질문에 맞는 모델을 먼저 선택

Key 조회, Aggregate 저장, Partition 분산, Graph 순회 중 중요한 작업을 직접 표현합니다.

등장 이유: 2000년대의 대규모 인터넷 서비스는 수천 대 서버로 확장되는 저장과 높은 가용성을 요구했습니다. Bigtable과 Dynamo 같은 시스템은 범용 관계형 모델 대신 특정 접근 방식과 분산 요구에 맞춘 설계를 보여주었고, 이 흐름이 여러 NoSQL 계열로 이어졌습니다.

NOSQL이 잘 맞는 경우

주요 접근 패턴이 분명하다

  • 함께 읽고 쓰는 중첩 데이터를 한 Aggregate로 다룬다.
  • Document마다 Field 구성이 다르거나 자주 변한다.
  • Key·Partition 중심으로 여러 Node에 분산해야 한다.
RDBMS가 잘 맞는 경우

관계와 범용 질의가 중심이다

  • 여러 종류의 데이터를 다양한 방식으로 Join한다.
  • Foreign Key와 Constraint로 관계 무결성을 강하게 지킨다.
  • 정형화된 Schema와 복잡한 Transaction이 핵심이다.
RDBMS의 기본 관점

관계를 정규화한 Table

ordersid · customer_id · status · total
order_itemsorder_id · sku · qty · price
addressescustomer_id · city · postal_code

명시적 Schema, Constraint, Join과 범용 Query가 강점입니다.

↔
Document DB의 기본 관점

Aggregate를 한 Document로

orders / _id: 1001customerId · address {…}
items [{…}] · status · total

Aggregate는 함께 읽고 갱신하는 업무 데이터 묶음입니다. 중첩 구조와 이 단위의 원자적 갱신이 강점입니다.

여기서 비교하는 것은 논리적 데이터 모델입니다. Page·Cache·파일처럼 bytes를 저장하는 방식은 별도의 저장 엔진 문제이며 3번째 페이지에서 다룹니다.

현대 RDBMS와 MongoDB의 경계가 겹치는 이유

현대 RDBMS도 JSON·분산 기능을 제공하고 MongoDB도 Schema validation, Index, $lookup, ACID transaction을 제공합니다. 차이는 기능의 유무보다 기본 모델과 최적화의 중심입니다.
