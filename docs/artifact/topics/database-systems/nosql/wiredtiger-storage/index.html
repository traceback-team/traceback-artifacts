01 · BOUNDARY

논리 구조와 물리 구조는 어디서 갈라질까?

사용자가 보는 이름과 Storage engine이 관리하는 구조는 같은 층이 아닙니다.

MongoDB 논리 계층 ↔ WiredTiger 물리 계층

번역 →
PHYSICAL · WIREDTIGER / OS

Key·Value와 bytes의 세계

WiredTiger Table / B-tree

Collection data와 각 Index의 구조

Record

Record key와 BSON value bytes

Internal / Leaf Page

Cache에서 탐색·변경되는 B-tree 단위

.wt block · Journal record

압축된 Page block과 복구 기록

정확한 표현: WiredTiger는 “아무것도 모르는” 것이 아니라 업무 의미를 모릅니다. Key·Value, B-tree, Page, timestamp와 압축은 알지만 그 bytes가 주문의 배송지인지 판단하지 않습니다.

02 · PAGE

Document는 어떻게 파일 bytes가 될까?

Document 하나가 Page 하나가 되는 것이 아닙니다. 여러 Record가 B-tree Page에 놓이고, memory의 변경된 Page가 disk image로 조정됩니다.

MONGOD OUTPUTRecord operation

Collection·Index key/value 읽기·쓰기

BTREEInternal / Leaf Page

Key를 따라 leaf의 Record에 접근

MEMORYWiredTiger Cache

Page를 읽고 변경 상태 유지

RECONCILECompress / Block

변경을 on-disk Page image로 생성

OS / DISK.wt file bytes

Collection·Index별 파일과 metadata

ed000000 10 5f696400 e9030000 10 637573746f6d65724964 ...

주문 BSON은 237 bytes였습니다. 첫 4 bytes의 little-endian 값 0x000000ed도 전체 길이 237을 뜻합니다.

03 · INDEX ADDRESS

인덱스는 Document의 어디를 가리킬까?

같은 _id: 1001을 찾되, 역사적 MMAPv1과 현재 WiredTiger가 인덱스 다음에 무엇을 따라가는지 비교합니다.

MMAPv1 · MongoDB 3.2 source ↔ WiredTiger · MongoDB 7.0.41

1. 인덱스에는 어떤 값이 저장되어 있는가?

두 엔진 모두 B-tree에서 _id: 1001을 찾지만, leaf가 돌려주는 참조의 의미가 다릅니다.

MMAPv1물리 위치 참조
QUERY_id: 1001
→
INDEX B-TREE LEAF_id: 1001
→
INDEX VALUEDiskLoc
file 2 · offset 4096

DiskLoc은 32-bit 파일 번호와 32-bit byte offset을 묶은 64-bit 위치입니다.

WiredTiger논리 식별자 참조
QUERY_id: 1001
→
INDEX B-TREE LEAF_id: 1001
→
INDEX VALUERecordId
42

RecordId는 Record Store 안의 Document를 다시 찾는 식별자이며 파일 offset이 아닙니다.

2. 실제 Document의 위치와 크기는 어떻게 알 수 있는가?

MMAPv1은 파일의 시작점에서 offset만큼 이동하고, WiredTiger는 Record Store B-tree를 한 번 더 탐색합니다.

MMAPv1 · DiskLoc으로 바로 이동예시 값
orders.2파일 시작 0 byte
앞부분
0 … 4095 B
Record headerlengthWithHeaders
BSON Document첫 4 B에도 BSON 길이
↳ file 시작 + offset 4096에서 읽기 시작↔ header의 lengthWithHeaders까지가 할당 Record

Offset은 해당 data file의 시작을 기준으로 합니다. Record header는 할당된 전체 길이를, BSON의 첫 4 bytes는 실제 BSON 길이를 알려줍니다.

WiredTiger · Record Store에서 다시 탐색개념 예시
INDEX OUTPUTRecordId 42
→
RECORD STORE B-TREEkey 42 탐색
→
RecordId 41
RecordId 42
BSON value
RecordId 43
반환된 RecordData의 buffer + size → BSON Document 237 B

RecordId에는 물리 위치나 크기가 없습니다. WiredTiger가 Page·Block을 해석해 value를 돌려주며, 호출자는 반환된 길이와 BSON 길이를 봅니다.

3. 데이터의 저장 위치가 바뀌면 무엇이 달라지는가?

같은 Document가 더 큰 공간으로 옮겨지는 상황에서 인덱스가 영향을 받는지를 봅니다.

MMAPv1Document가 기존 Record보다 커짐
BEFOREDiskLoc 2:4096기존 Record 공간
→
AFTERDiskLoc 3:8192새 Record 공간
인덱스의 물리 참조도 새 DiskLoc으로 갱신

Document가 새 Record로 이동하면 identity가 된 위치가 바뀌므로, 그 Document를 가리키는 인덱스 참조도 바뀝니다.

WiredTigerPage split·reconcile로 bytes가 재배치됨
BEFOREBlock A · Page PRecordId 42의 bytes
→
AFTERBlock C · Page QRecordId 42의 bytes
인덱스의 RecordId 42는 그대로 유지

물리 Page와 Block이 달라져도 논리 식별자는 유지됩니다. Record Store B-tree와 WiredTiger metadata가 새 배치를 해결합니다.

한 문장 차이: MMAPv1 인덱스는 “파일의 이 위치”를 가리키고, WiredTiger 인덱스는 “Record Store의 이 Record”를 가리킵니다.

04 · MECHANISMS

Index·Transaction·WAL은 어느 층에 있을까?

사용자가 선언하는 논리 기능과 WiredTiger의 물리 메커니즘이 협력합니다.

INDEX

별도 B-tree 탐색 구조

Query: customerId=7, status=PAID
mongod Planner가 customer_status 선택
WiredTiger Index key → Record

Index 정의·Plan 선택은 mongod, Index Page·파일 갱신은 WiredTiger 책임입니다.

TRANSACTION

여러 변경을 한 단위로 Commit

Session + txnNumber 3
Alice −15,000 · Bob +15,000
commitTransaction → 둘 다 공개

한 Document 쓰기는 원자적입니다. 여러 Document를 모두 적용하거나 취소할 때 transaction을 사용합니다.

WAL / JOURNAL

원리는 WAL, replica set은 Oplog와 협력

일반 WAL: Data Page보다 복구 기록이 먼저
MongoDB 7 replica set: 사용자 Table 직접 logging은 끔
Journal의 Oplog → stable checkpoint 뒤 재적용

이 Lab처럼 --replSet으로 실행하면 사용자 Collection·Index 변경에는 대응하는 Oplog entry가 생깁니다. local.oplog.rs는 Journal로 보호되고, 시작 복구는 stable checkpoint 이후 필요한 Oplog를 적용합니다.

WiredTiger Journal

한 mongod에서 선택된 Table의 물리 복구용 WAL. 이 replica set 구성에서는 Oplog를 보호합니다.

Replication Oplog

논리 변경 기록이자 member 간 복제 입력. 같은 Node의 시작 복구에서도 stable checkpoint 이후 변경을 전진 적용하는 근거가 됩니다.
