02 · I/O UNITS

파일의 한 byte를 찾으면 장치도 한 byte만 읽을까?

아닙니다. DBMS는 파일의 byte 범위를 논리적으로 지정하지만, OS·Filesystem·SSD/HDD는 각자 정한 더 큰 단위로 이를 운반하고 저장합니다.

DATABASE ENGINERecord · DB Page

WiredTiger가 B-tree key/value와 Page를 해석

FILE COORDINATEoffset + length

파일 시작에서 몇 byte 떨어진 범위를 읽을지 지정

OPERATING SYSTEMOS Page Cache

파일 내용을 memory page에 보관하고 재사용

FILESYSTEMFilesystem Block

파일의 논리 범위를 저장 공간 block에 배치

SSD / HDDLogical Block I/O

장치가 노출한 sector·block 주소로 실제 요청 처리

Random Access의 정확한 뜻: 프로그램이 파일 전체를 앞에서부터 읽지 않고 offset + length로 원하는 byte 범위를 지정할 수 있다는 뜻입니다. 실제 장치가 한 byte씩 읽는다는 뜻은 아닙니다.

FILE SIZE계속 변하는 byte 길이DBMS가 생성·확장하고 Filesystem이 metadata로 기록
DB PAGE엔진 설정·형식PostgreSQL·InnoDB·WiredTiger가 각자 결정
OS PAGEKernel / CPU architecture4KB가 흔하지만 고정 보편값은 아님
FILESYSTEM BLOCKFilesystem 생성 설정ext4는 4KB가 흔하지만 1–64KB 가능
DEVICE BLOCK장치·Controller512B/4KiB logical block 등이 있으며 내부 단위와 다를 수 있음

DBMS마다 “Page”도 같은 크기와 의미일까?

같지 않습니다. 고정 Page를 쓰는 엔진과, 최대 크기를 기준으로 split·compression하는 엔진을 구분해야 합니다.

POSTGRESQL 18

고정 DB Page

보통 8KB이며 build 시 결정. Table과 Index 모두 같은 고정 Page 배열.

INNODB 8.4

고정 Tablespace Page

기본 16KB. Instance 초기화 때 4–64KB 중 정하고 이후 고정.

MMAPV1 · 역사적

가변 Record 슬롯

DB 고정 Page보다 가변 길이 Record를 Extent 안에 할당. OS memory page는 별도로 존재.

WIREDTIGER 7.0.41

최댓값 기반 Page

internal 4KB·leaf 32KB는 관찰한 최대 설정. split·compression 뒤 실제 on-disk block 크기는 달라질 수 있음.

더 넓은 DBMS 파일 구조는 저장 구조를 읽는 세 층과 PostgreSQL · InnoDB 탐색기에서 이어집니다.

03 · INDEX ADDRESS

인덱스는 Document의 어디를 가리킬까?

같은 _id: 1001을 찾되, 역사적 MMAPv1과 현재 WiredTiger가 인덱스 다음에 무엇을 따라가는지 비교합니다.

MMAPv1 · MongoDB 3.2 source ↔ WiredTiger · MongoDB 7.0.41
MONGOD CATALOGIndex 정의

필드·정렬 방향·이름 같은 논리 metadata

→
WIREDTIGER TABLEindex-… .wt

B-tree key와 RecordId를 Page·Block으로 디스크에 지속

↔
MEMORYWiredTiger Cache

자주 쓰는 Index Page를 memory에 올려 탐색

중요한 교정: MongoDB Index는 재시작하면 사라지는 임시 구조가 아니라 디스크에 지속되는 B-tree입니다. WiredTiger Index에 저장하지 않는 것은 “현재 SSD의 절대 물리 주소”이며, 대신 RecordId를 지속합니다. Cache와 영속성, Journal 적용 여부는 서로 다른 문제입니다.

1. 인덱스에는 어떤 값이 저장되어 있는가?

두 엔진 모두 B-tree에서 _id: 1001을 찾지만, leaf가 돌려주는 참조의 의미가 다릅니다.

MMAPv1물리 위치 참조
QUERY_id: 1001
→
INDEX B-TREE LEAF_id: 1001
→
INDEX VALUEDiskLoc
file 2 · offset 4096

DiskLoc은 32-bit 파일 번호와 32-bit byte offset을 묶은 64-bit 위치입니다.

WiredTiger논리 식별자 참조
QUERY_id: 1001
→
INDEX B-TREE LEAF_id: 1001
→
INDEX VALUERecordId
42

RecordId는 Record Store 안의 Document를 다시 찾는 식별자이며 파일 offset이 아닙니다.

2. 실제 Document의 위치와 크기는 어떻게 알 수 있는가?

MMAPv1은 파일의 시작점에서 offset만큼 이동하고, WiredTiger는 Record Store B-tree를 한 번 더 탐색합니다.

3. 데이터의 저장 위치가 바뀌면 무엇이 달라지는가?

같은 Document가 더 큰 공간으로 옮겨지는 상황에서 인덱스가 영향을 받는지를 봅니다.

MMAPv1Document가 기존 Record보다 커짐
BEFOREDiskLoc 2:4096기존 Record 공간
→
AFTERDiskLoc 3:8192새 Record 공간
인덱스의 물리 참조도 새 DiskLoc으로 갱신

Document가 새 Record로 이동하면 identity가 된 위치가 바뀌므로, 그 Document를 가리키는 인덱스 참조도 바뀝니다.

WiredTigerPage split·reconcile로 bytes가 재배치됨
BEFOREBlock A · Page PRecordId 42의 bytes
→
AFTERBlock C · Page QRecordId 42의 bytes
인덱스의 RecordId 42는 그대로 유지

물리 Page와 Block이 달라져도 논리 식별자는 유지됩니다. Record Store B-tree와 WiredTiger metadata가 새 배치를 해결합니다.

한 문장 차이: MMAPv1 인덱스는 “파일의 이 위치”를 가리키고, WiredTiger 인덱스는 “Record Store의 이 Record”를 가리킵니다.

04 · WHY WIREDTIGER

MMAPv1의 어떤 한계를 바꾸려고 했을까?

WiredTiger는 단순히 파일 형식만 바꾼 것이 아니라 위치 참조·동시성·압축과 Cache 책임을 함께 바꿨습니다. MMAPv1은 MongoDB 4.2에서 제거된 역사적 엔진입니다.

MMAPV1 · GROWING DOCUMENT더 큰 Record 공간으로 이동

기존 슬롯보다 Document가 커지면 새 Record를 할당하고 그 Document를 가리키는 Index 참조를 고쳐야 했습니다.

→
WIREDTIGER고정 RecordId + Page 재구성

논리 identity를 유지한 채 Record Store B-tree와 Page split·reconcile이 물리 배치를 처리합니다.

MMAPV1 · CONCURRENCY거친 잠금 단위

동시에 다른 Document를 갱신하는 작업이 서로 막을 가능성이 컸습니다.

→
WIREDTIGERDocument-level concurrency + MVCC

다른 Document의 쓰기를 병행하고 snapshot으로 일관된 읽기 관점을 제공합니다.

MMAPV1 · MEMORY / SPACEMemory-mapped 파일과 가변 Record

OS page cache에 크게 의존했고, Document 이동·빈 공간과 uncompressed BSON 비용을 관리해야 했습니다.

→
WIREDTIGERInternal Cache + Compression

WiredTiger Cache와 filesystem cache를 함께 사용하고 Collection·Index Page를 압축할 수 있습니다.

“파일 중간을 수정하면 뒤의 모든 offset이 바뀐다”는 설명이 왜 부정확한가?

MMAPv1은 일반 text file처럼 중간에 bytes를 끼워 넣고 뒤 데이터를 통째로 밀지 않습니다. 커진 Document는 다른 빈 Record 슬롯으로 이동하고 그 Document를 가리키는 Index 참조가 갱신됩니다.

MyISAM도 Index가 data-file pointer를 쓰지만 Dynamic Row가 커지면 조각을 pointer로 연결할 수 있습니다. 이 계열의 실제 문제는 모든 뒤쪽 offset의 일괄 변경이 아니라 이동·fragmentation·pointer 유지와 복구 비용입니다.

05 · TRANSACTION & RECOVERY

여러 변경을 묶고 Crash 뒤 복구하는 것은 누구의 일일까?

Index는 앞 절에서 다뤘으므로 반복하지 않고, Transaction과 WAL·Oplog의 서로 다른 목적만 연결합니다.

TRANSACTION

여러 변경을 한 단위로 Commit

Session + txnNumber 3
Alice −15,000 · Bob +15,000
commitTransaction → 둘 다 공개

한 Document 쓰기는 원자적입니다. 여러 Document를 모두 적용하거나 취소할 때 transaction을 사용합니다.

WAL / JOURNAL

원리는 WAL, replica set은 Oplog와 협력

일반 WAL: Data Page보다 복구 기록이 먼저
MongoDB 7 replica set: 사용자 Table 직접 logging은 끔
Journal의 Oplog → stable checkpoint 뒤 재적용

이 Lab처럼 --replSet으로 실행하면 사용자 Collection·Index 변경에는 대응하는 Oplog entry가 생깁니다. local.oplog.rs는 Journal로 보호되고, 시작 복구는 stable checkpoint 이후 필요한 Oplog를 적용합니다.

WiredTiger Journal과 Replication Oplog의 차이
WiredTiger Journal

한 mongod에서 선택된 Table의 물리 복구용 WAL. 이 replica set 구성에서는 Oplog를 보호합니다.

Replication Oplog

논리 변경 기록이자 member 간 복제 입력. 같은 Node의 시작 복구에서도 stable checkpoint 이후 변경을 전진 적용하는 근거가 됩니다.
