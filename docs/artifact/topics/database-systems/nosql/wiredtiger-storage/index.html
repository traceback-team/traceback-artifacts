01 · BOUNDARY

논리 구조와 물리 구조는 어디서 갈라질까?

mongod는 Document의 의미를 해석하고, WiredTiger는 그 결과를 key와 bytes로 저장합니다. 저장 엔진은 주문·배송지 같은 업무 의미를 모르지만 B-tree, Page, timestamp와 압축은 압니다.

02 · UNITS

Record, Page, Block은 무엇이 다를까?

Record는 한 건, Page는 여러 Record를 관리하는 엔진 단위, Block은 파일·장치 계층의 저장 단위입니다. 같은 “Block”이라도 계층이 다르면 크기와 역할이 다릅니다.

용어의미크기 결정
Record저장 엔진이 한 건으로 다루는 key/value데이터에 따라 달라짐
Page여러 Record·Index entry를 묶어 탐색·캐시하는 단위스토리지 엔진의 형식과 설정
Block파일시스템·저장장치가 공간과 I/O를 관리하는 단위해당 계층의 설정과 장치
WIREDTIGERRecord / Page
FILEoffset + length
OS / FILESYSTEMPage cache / Block
SSD / HDDBlock I/O

Random Access는 파일 전체를 순서대로 읽지 않고 원하는 byte 범위를 지정한다는 뜻입니다. 저장장치가 한 byte씩 읽는다는 뜻은 아닙니다.

참고 · 계층별 크기와 다른 DBMS의 Page 비교

파일 크기는 계속 변하고, OS Page·Filesystem Block·Device Block은 각각 Kernel·Filesystem·장치가 정합니다. 4KB가 흔해도 보편적인 고정값은 아닙니다.

PostgreSQL 18고정 Page · 보통 8KB
InnoDB 8.4고정 Page · 기본 16KB
MMAPv1Extent 안의 가변 Record 슬롯
WiredTiger 7.0.41최대값 기반 Page · 압축 Block은 가변

Lab에서 WiredTiger의 최대 설정은 internal 4KB·leaf 32KB였습니다. 이는 모든 디스크 Block이 그 크기라는 뜻이 아닙니다.

03 · INDEX

인덱스는 Document를 어떻게 찾아갈까?

MMAPv1은 파일 위치인 DiskLoc을, WiredTiger는 Record Store의 논리 식별자인 RecordId를 저장합니다. 그래서 일반 Collection의 _id 조회는 Index B-tree와 Record Store B-tree를 차례로 탐색합니다.

04 · WHY

왜 MMAPv1에서 WiredTiger로 전환했을까?

목표는 물리 위치 변화의 부담을 줄이고, 동시성·캐시·압축을 저장 엔진이 더 정교하게 관리하는 것이었습니다. MMAPv1은 MongoDB 4.2에서 제거된 역사적 엔진입니다.

문제 축MMAPv1WiredTiger얻는 것
Record 이동DiskLoc 참조 갱신→RecordId + B-tree Page 재구성논리 식별자 유지
동시성상대적으로 거친 잠금→Document 수준 동시성 + MVCC병행 쓰기와 snapshot 읽기
메모리·공간OS mmap 중심·비압축 BSON→자체 Cache + Page 압축Cache 제어와 공간 절약
정확성 참고 · “파일 중간 수정 시 뒤 offset이 모두 바뀐다”는 설명

MMAPv1은 text file처럼 중간에 bytes를 삽입해 뒤 데이터를 전부 밀지 않습니다. 커진 Document를 다른 Record 슬롯으로 옮기고, 그 Document를 가리키는 DiskLoc 참조를 바꿉니다. 실제 비용은 이동·fragmentation·pointer 유지입니다.

05 · SAFETY

Transaction, Journal, Oplog은 각각 무엇을 지킬까?

Transaction은 변경의 원자성을, Journal은 같은 Node의 Crash 복구를, Oplog은 replica set의 논리 변경 전달을 담당합니다. 셋은 서로 협력하지만 같은 기록이 아닙니다.

ATOMICITY

Transaction

여러 Document 변경을 모두 Commit하거나 모두 취소하는 실행 경계입니다.

DURABILITY / RECOVERY

WiredTiger Journal

선택된 WiredTiger Table의 변경을 보호해 같은 Node의 Crash 복구에 사용합니다.

REPLICATION

Replication Oplog

논리 변경을 순서대로 기록해 다른 member가 재생하게 합니다.

참고 · replica set에서 Journal과 Oplog이 함께 복구하는 방식

MongoDB 7 replica set에서는 Oplog 자체가 Journal로 보호됩니다. Node는 stable checkpoint를 기준으로 시작하고 필요한 Oplog 변경을 전진 적용할 수 있습니다. 따라서 Journal을 “복제 로그”, Oplog을 “WAL 파일”로 바꾸어 부르면 안 됩니다.
