# MongoDB Clustered Collection 관찰 · 2026-11-20

## 실행 환경

- Docker Client / Server: `29.7.2`
- Docker Server OS / Architecture: Linux / `arm64`
- MongoDB: `7.0.41`
- 구성: `labs/nosql-mongodb-architecture/compose.yaml`의 단일 Node Replica Set

## 확인한 내용

일반 Collection과 다음 옵션으로 만든 Clustered Collection에 같은 세 Document를
넣고 `_id: 1002`를 조회했다.

```javascript
db.createCollection("clustered", {
  clusteredIndex: { key: { _id: 1 }, unique: true, name: "_id_" }
})
```

- 일반 Collection의 winning plan: `IDHACK`
- Clustered Collection의 winning plan: `CLUSTERED_IXSCAN`
- Clustered scan 범위: `minRecord: 1002`, `maxRecord: 1002`
- `listCollections`의 options에 `clusteredIndex.key: { _id: 1 }`이 기록됨

이 결과는 일반 Collection의 별도 `_id` Index 경로와 달리, Clustered Collection이
`_id` 값을 Record Store의 key와 저장 순서로 사용한다는 MongoDB 7.0 문서 설명과
일치한다. Clustered Collection 기능 자체는 MongoDB `5.3`부터 제공된다.

검증 뒤 테스트용 `clustered_check` Database를 삭제하고 Docker Compose 구성을
종료했다. Secondary Index를 통한 Clustered Collection 조회 경로와 성능 차이는
이번 관찰 범위에 포함하지 않았다.
