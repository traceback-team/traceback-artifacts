# 2026-11-09 관찰 기록

`docker compose up -d --wait` 뒤 `./verify.sh`를 실행한 결과입니다. 아래의 결론은
이 이미지와 초기 스키마에서 직접 관찰한 범위로 제한합니다.

## 실행 대상

- PostgreSQL `18.6`, image digest
  `postgres@sha256:e3d24f6906d0760bf4da0dae872415391ededefad23fd471c47dc53b0ddf3c42`
- MySQL `8.4.13`, image digest
  `mysql@sha256:a81d043930e51745522bd5c430961cf8286f0a23f0a9a2a6e0108f7ea71b0902`
- 두 Container 모두 Health Check 통과

## PostgreSQL에서 관찰한 것

```text
PID 1                         postgres
default_table_access_method   heap
pg_am의 Table AM              heap → heap_tableam_handler
pg_am의 Index AM              brin, btree, gin, gist, hash, spgist
accounts의 Table AM           heap
accounts의 Relation File      base/16384/16385
WAL Directory                 /var/lib/postgresql/18/docker/pg_wal
```

`pg_stat_activity`에는 `checkpointer`, `background writer`, `walwriter`,
`autovacuum launcher`, `io worker`, `client backend` 등이 서로 다른
`backend_type`으로 관찰되었습니다. 이 결과는 PostgreSQL Runtime이 하나의
“heap engine process”로 노출되는 것이 아니라 PostgreSQL Server의 여러 공용
Backend 역할로 동작한다는 사실을 보여 줍니다.

이 실험에서 확인한 PostgreSQL Table AM은 `heap` 하나뿐입니다. PostgreSQL에
외부 Table AM을 설치할 수 없다는 뜻은 아니며, 이 Stock Image에서 MySQL의
InnoDB/MyISAM 같은 복수 선택이 준비되어 있지 않다는 뜻입니다.

## MySQL에서 관찰한 것

```text
PID 1                         mysqld --default-storage-engine=InnoDB
default_storage_engine        InnoDB
accounts의 Engine             InnoDB
accounts의 File               /var/lib/mysql/engine_lab/accounts.ibd
활성 Storage Engine 예         InnoDB, MyISAM, MEMORY, CSV, ARCHIVE, BLACKHOLE
```

같은 `engine_switch_probe` Table을 먼저 `ENGINE=InnoDB`로 만들고 다음 명령을
실행한 뒤 `information_schema.TABLES.ENGINE`이 `MyISAM`으로 바뀐 것을 확인했습니다.

```sql
ALTER TABLE engine_lab.engine_switch_probe ENGINE=MyISAM;
```

`information_schema.PLUGINS`에서는 InnoDB와 MyISAM이 `ACTIVE`인
`STORAGE ENGINE`으로 나타났고 `PLUGIN_LIBRARY`는 `NULL`이었습니다. 따라서 이
환경에서 “Pluggable”은 별도 DB Server Process라는 뜻이 아니며, 두 Engine은
같은 `mysqld`가 노출하는 논리적 Engine 경계입니다.

`performance_schema.threads`에서는 여러 Background Thread와
`thread/innodb/io_read_thread`, `thread/innodb/io_write_thread`,
`thread/innodb/dict_stats_thread` 같은 InnoDB 소유 Thread 이름을 확인했습니다.

## 이 관찰로 말할 수 있는 범위

직접 확인된 가장 큰 차이는 다음과 같습니다.

- MySQL은 실행 중인 한 Server에서 복수 Storage Engine을 열거하고 Table의
  `ENGINE` 값을 InnoDB에서 MyISAM으로 변경할 수 있었습니다.
- PostgreSQL은 Access Method Catalog를 노출했지만, 이 Stock Image의 Table AM은
  `heap` 하나였고 Buffer/WAL 관련 역할은 PostgreSQL Backend Type과 Directory로
  별도 관찰되었습니다.
- 두 제품 모두 Engine/Access Method가 별도 Network DB Server라는 증거는 없었습니다.
  PostgreSQL PID 1은 `postgres`, MySQL PID 1은 `mysqld`였습니다.

이 결과만으로 모든 Extension 구현 가능성이나 Source Code의 전체 책임을 단정하지
않습니다. 문서에는 위 명령으로 재현 가능한 사실과 그 범위만 “Docker 관찰”로 표시합니다.
