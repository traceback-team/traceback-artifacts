# MongoDB 주문 조회 지연 경계 분해 · 2026-11-21

## 질문

`db.orders.findOne({ _id: 1001 })`은 Index Key와 Document를 하나씩만 읽는데,
Client에서 관찰한 지연은 왜 PostgreSQL JSONB 한 Row 조회보다 길었는가?

## 측정 방법

- MongoDB `7.0.41`, Node.js Driver `7.9.0`
- 기존 비교 실험과 같은 Docker Network·warm cache·단일 Node 구성
- 같은 `_id` 조회를 200회 예열한 뒤 5,000회 순차 실행
- Client의 전체 경과 시간과 조회 전후
  `serverStatus.opLatencies.reads` 누적값 차이를 비교

## 관찰값

| 범위 | 요청당 평균 | 전체 중 비중 |
|---|---:|---:|
| Client에서 본 전체 요청 | 0.270 ms | 100% |
| MongoDB 서버 내부 Read | 0.045 ms | 16.6% |
| 서버 밖 경계 | 0.225 ms | 83.4% |

실행 계획도 `_id` 전용 경로인 `IDHACK`으로 Index Key `1`개와 Document `1`개만
검사했다. 따라서 이 조건에서 MongoDB Client 지연의 주원인은 Record 탐색이나
WiredTiger I/O가 아니라 Driver·BSON 직렬화/역직렬화·Docker Network Socket·
Event Loop Scheduling을 합친 서버 밖 경계 비용이다.

이 측정으로 서버 밖 0.225 ms를 Driver, BSON, Socket, Event Loop 각각의 값으로
다시 배분할 수는 없다. 그러므로 “MongoDB 문서 모델이 느리다” 또는 그중 한
요소만이 원인이라고 단정하지 않는다.

## SKU 주문 수 조회 후속 분석

기존 100회 측정에서는 PostgreSQL JSONB `0.267 ms`, MongoDB `0.558 ms`로
MongoDB가 약 2배 길었다. 같은 쿼리를 1,000회씩 5세트로 늘려 다시 측정했다.

| 범위 · 5세트 중앙 | PostgreSQL JSONB | MongoDB |
|---|---:|---:|
| Client 전체 | 0.254 ms | 0.279 ms |
| DB 서버 내부 | 0.133 ms | 0.088 ms |
| 서버 밖 경계 | 0.121 ms | 0.191 ms |

- Client 세트 평균 범위: JSONB `0.241–0.394 ms`, MongoDB `0.269–0.402 ms`
- PostgreSQL: GIN 후보 `184`개, Heap Row `75`개 확인,
  Shared Buffer hit 평균 `86`개/호출, Physical read `0`
- MongoDB: Multikey Index의 `COUNT_SCAN`, Key `76`개, Document `0`개,
  WiredTiger cache page/byte read 증가 `0`

확인된 사실은 두 가지다. 첫째, 기존의 2배 차이는 5세트에서 재현되지 않았고
MongoDB Client 시간은 JSONB보다 `1.02–1.24배` 길었다. 둘째, MongoDB 서버
실행은 오히려 더 짧았지만 서버 밖 경계가 약 `0.070 ms` 더 길어 전체 응답이
조금 길어졌다. 따라서 이 차이를 MongoDB의 Index 탐색이나 Document 접근
비용으로 설명할 수 없다.

확인하지 못한 부분은 MongoDB 서버 밖 `0.191 ms`를 Driver, BSON, Socket,
Event Loop 각각으로 배분한 값과, 과거 100회 측정 한 번에서 발생한 큰 변동의
단일 원인이다. 당시의 상세 trace가 없으므로 이를 사후에 특정하지 않는다.
